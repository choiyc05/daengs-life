## D-001. 크롤링 오케스트레이션: Celery + Beat (+ Redis) — ✅ 확정 (2026-08-19)

**배경** — 크롤링 시스템화 요구사항 3개: ① 주기 실행 ② 관리자페이지 수동 트리거 ③ 원하는 소스만 선택 실행. 팀 초기 안은 Airflow.

**결정** — Celery(작업 큐) + Celery Beat(스케줄러) + Redis(브로커·결과 백엔드). FastAPI 백엔드와 같은 코드베이스/이미지 사용.

**근거**
- 요구사항의 실체는 "작업 큐 + 스케줄러 + 실행 이력"이지 워크플로 엔진이 아님 — 태스크 의존성 그래프가 없고, cadence는 cron 표현식 몇 개 수준
- Airflow는 고정비(상주 RAM 1~2GB, logical date/catchup 등 개념 학습, 느린 개발 루프)가 규모(소스 30개, 하루 몇 회) 대비 과함
- 성능은 두 안이 갈리지 않음 — 병목은 크롤링 자체(요청 간격 1~2초의 네트워크 I/O, PDF 파싱, 임베딩)
- Redis는 실시간 조회형 파트에서 API 응답 TTL 캐시로 재활용 예정 (컨테이너 하나, 두 역할)
- Kafka는 브로커로 부적합: 오프셋 기반 스트림 로그 모델 vs 태스크별 ack/재큐잉 의미론 불일치, Celery 공식 미지원

**대안 요약**

| | APScheduler | Celery+Beat (채택) | Airflow |
|---|---|---|---|
| 추가 인프라 | 0 | Redis + worker + beat | 스케줄러+웹서버+메타DB |
| 재시도/이력 UI | 직접 구현 / ❌ | 데코레이터 / △(Flower) | ✅ / ✅ |
| 리스크 | 백엔드 재시작 시 작업 소실 | 이력 직접 기록 필요 | 무게·학습 곡선 |

**구현 시 준수할 아키텍처 원칙**
1. `crawler/`는 오케스트레이터 무관 순수 파이썬 패키지 + CLI(`python -m crawler run --source X`). Celery 태스크는 호출만 — 갈아타기 비용 ≈ 0
2. fetch(원본 수집)와 index(청킹→임베딩→적재) 태스크 분리. 콘텐츠 sha256으로 변경 감지 → 무변경 문서는 재임베딩 스킵
3. 실행 이력은 Postgres `crawl_runs` 테이블(source_id, status, docs_fetched, docs_changed, error, started_at, finished_at). 관리자페이지는 이 테이블을 읽음(Flower는 운영 보조)
4. 소스별 cadence는 seed_sources.yaml에 스케줄 힌트로: 공고 daily / 안내페이지 weekly / 약관 quarterly / 법령 manual. Beat는 "due 소스 선별" 태스크 하나만 주기 등록, 수동 트리거는 `source_ids` 인자로 같은 경로를 override
5. 소스당 독립 태스크 — 한 소스 실패가 전체를 막지 않음. `autoretry_for` + 지수 백오프(max_retries=3)
6. 관리자 트리거 흐름: Next.js → FastAPI `POST /admin/crawl {source_ids}` → 태스크 `.delay()` → 상태는 crawl_runs 폴링

**compose 토폴로지** — `redis` / `backend`(FastAPI) / `worker` / `beat`. worker·beat는 backend와 동일 이미지, command만 상이. broker=`redis://redis:6379/0`, result_backend=`redis://redis:6379/1`

**트레이드오프 수용** — 실행 이력 UI 부재 → crawl_runs 자체 구현(관리자페이지용으로 어차피 필요). Celery 워커의 Windows 네이티브 미지원 → 도커 실행(기존 방침과 동일)

## D-002. 임베딩 모델 — ✅ 후보 3종 확정 (2026-08-20), 승자는 베이크오프 후

**차원 1024 유지 — 근거를 바꿔 기록한다.** "누가 정해놔서"가 아니라 세 가지가 수렴시킨다:
1. **모델이 강제** — 후보 3종이 전부 1024 native다. 자를 필요도 재정규화할 필요도 없다
2. **pgvector HNSW 2000차원 상한** (0.8.6 실측: `vector(2001)` → `cannot have more than 2000 dimensions`). gemini 3072 은 `halfvec` 우회가 필요해 복잡도를 산다
3. **저장 비용은 무관** — 청크 3,000개 기준 `3,000 × 1024 × 4B ≈ 12MB`. 판단 근거에서 뺀다

| # | 모델 | 차원 | 컨텍스트 | 라이선스 | 역할 |
|---|---|---|---|---|---|
| 1 | `BAAI/bge-m3` | 1024 | 8,192 | MIT | 기준선 (다국어) |
| 2 | `nlpai-lab/KURE-v1` | 1024 | 8,192 | BGE-M3 파생 | 한국어 파인튜닝 효과 |
| 3 | `Qwen/Qwen3-Embedding-0.6B` | 1024 (MRL 32~1024) | 32,768 | Apache 2.0 | 계열 다름 + 영어 |

**KURE-v1 은 BGE-M3 를 한국어 200만 쿼리-문서 쌍으로 파인튜닝한 모델**이라 1↔2 는 "같은 베이스에 한국어 튜닝이 이득인가"를 재는 **통제 비교**다. 세 번째는 계열을 달리해야 한 가지를 세 번 재지 않는다.

**3번을 Qwen3-0.6B 로 고른 근거** (2026-08-20 리더보드 확인) — MTEB 다국어 retrieval 80.83 / 평균 64.33 으로 1GB 미만 최상위권. 상위 모델(KaLM-Gemma3-12B 72.32, Qwen3-8B 70.58)은 개발 PC 부담. 32k 컨텍스트라 잘림 위험 0.

**영어가 필요한 실제 이유** — 코퍼스 계획에 WSAVA 백신 가이드라인(영문)이 있다. 한국어 전용 모델은 그 문서를 못 다룬다.

**탈락시킨 후보**
- `multilingual-e5-large` — 1024 차원이지만 **512 토큰 한계**. 우리 조문 p95 가 1,336자(≈900~1,300 토큰)라 **상위 10%가 조용히 잘린다.** 잘리는 게 보통 단서·예외 조항이라 법령 QA 에 치명적
- `gemini-embedding-001` — API 의존 + MRL 절단 시 재정규화 필요. 로컬 3종으로 충분
- `jina-embeddings-v3` — query/passage 어댑터가 매력적이나 **CC BY-NC(비상업)**

**구현 주의사항** (기존 유지)
- 베이크오프는 프로드 테이블 밖 **오프라인 스크립트**로 (`processed/embeddings/{model}.parquet`)
- 어떤 모델이든 `embedding_model` 기록 — 한 컬럼에 모델 혼입 금지
- 쿼리/문서 비대칭: 모델별 권장 프롬프트·task 구분을 따를 것
- 토큰 환산은 추정치다. 모델 확정 후 실제 토크나이저로 청크 길이 분포 재측정 (D-006)

**승자 판정 시점** — 골든셋이 100개 이상일 때. 그전 소규모 비교(14건)는 "명백히 나쁜 것을 거르는" 용도로만 쓴다 (n=10 이면 95% 신뢰구간 ±25%p, n=100 이면 ±7.8%p. 모델 간 차이는 보통 2~5%p).

## D-003. 검색 구성 (하이브리드·리랭커) — 🔶 제안 (논의중)

제안: v1 = 하이브리드 — pgvector dense + **Kiwi(kiwipiepy) 형태소 토큰화 → tsvector('simple') + GIN** lexical, **RRF(k=60)** 융합, 메타데이터 사전 필터(category·지역·시행일). 근거: 법률·행정 질의는 정확 용어("입마개", "제15조")가 승부처 — PG 기본 FTS는 한국어에 약해 형태소 토큰화 우회 필요. 리랭커는 `retrieve → (rerank) → generate`의 옵셔널 스테이지로 설계만 해두고 평가셋 recall@5 측정 후 도입 결정(후보: bge-reranker-v2-m3 로컬 / Cohere Rerank 3.5 API).

## D-004. 청킹 전략 — ✅ 확정 (2026-08-20, 질문 1~7 원문 검증 완료)

### 전략 선택: 구조 기반(structure-aware)

원문이 `<조문단위>/<항>/<호>/<별표단위>` 태그로 구조를 이미 명시한다. 경계를 그 태그에 맞춘다.

| 전략 | 판정 | 사유 |
|---|---|---|
| Fixed-size | ✗ | N자 절단이 별표 논리 행 한가운데(`20 │ 40`)와 항 두문/호 사이를 끊는다. 기준① 파탄 |
| Recursive (구분자 계층) | ✗ | `\n\n → \n` 로 구조를 *근사*하는 방식. 태그로 이미 가진 정보를 버리는 것이고, `제101조제3항제4호` 인용 문자열을 텍스트 위치에서 복원할 수 없다 |
| Semantic (유사도 골짜기) | ✗ | 경계가 비결정적이라 조항 번호와 어긋난다. KPI가 "조항 번호 인용"이라 치명적. 법령은 구조가 곧 의미 단위라 얻을 것도 없다 |
| **구조 기반** | **✅** | 경계 = 인용 단위(조/항/호, 별표 행, Q/A 쌍). 결정적이고 **청크 ID가 곧 인용 문자열**이 된다 |
| Docling | ⏸ 보류 | 파서 라이브러리라 2단계 영역. 현 소스는 이미 구조화된 XML/HTML이라 쓸 자리가 없다. **펫보험 약관 PDF·지자체 공고 HWP** 수집 시 재검토 |

### 기준을 잡은 방법 (이론이 아니라 질문에서 거꾸로)

`300~800토큰` 같은 숫자에서 시작하면 참·거짓을 가릴 수 없다. 순서를 뒤집었다:
1. 사용자가 실제로 할 질문을 적는다
2. 그 답이 원문 **어디**에 있는지 손으로 찾는다
3. **찾은 조각의 자연 경계**가 청크 경계다
4. 아래 4기준으로 검증한다

**검증 기준 4개**
1. **인용 가능성** — 청크 하나가 조항 하나를 가리킬 수 있는가. KPI 직결이라 1순위
2. **자기완결성** — 떼어놓고 읽어서 답이 되는가
3. **검색 단위 = 답변 단위** — 글자 수가 아니라 "사용자가 한 번에 알고 싶어 하는 덩어리". 과분할·과병합 양쪽을 막는다
4. **임베딩 입력 한계** — 유일한 하드 제약. 넘으면 뒷부분이 조용히 잘린다

**호 단위로 쪼개면 안 되는 이유** — 금액이 항 두문에만 있다.
```
③ 다음 각 호의 어느 하나에 해당하는 자에게는 100만원 이하의 과태료를 부과한다.   ← 금액
   4. 제15조제1항을 위반하여 등록대상동물을 등록하지 아니한 소유자                ← 금액 없음
```

**별표에서 헤더를 3종 복제해야 하는 이유** — `(단위: 만원)`이 999줄짜리 표 전체에 **단 한 번**(81줄) 나온다. 빠뜨리면 `20`이 20원인지 20만원인지 알 수 없다.
```
 81|  (단위: 만원)
 87|│위반행위 │근거 법조문 │과태료 금액 │
 93|│         │            │1차 │2차 │3차 이상│
129|│라. 소유자가 법 제15조제1항을 위반    │법 제101조 │20 │40 │60│
132|│여 등록대상동물을 등록하지 않은 경    │제3항제4호 │   │   │  │
```
**"행"은 물리적 줄이 아니다.** 한 논리 행이 2~3줄로 hard-wrap 되고 사이에 빈 줄이 2개씩 낀다(별표4는 999줄 중 실제 내용 1/3). 재조립 규칙: `가./나./다.`로 시작하는 줄이 새 행.

**easylaw 헤딩은 2층이고 소단위를 쓴다**

| 층 | 마커 | 크기 / 주제 수 |
|---|---|---|
| 대 | `인쇄체크` | ~2,000자 / **4개**(목줄+인식표+배설물+자연공원) → 기준③ 위반 |
| **소** | 소제목 줄 | **~700자 / 1개** → 채택 |

### 2단계(파서)로 넘기는 사항

- 조문 텍스트에 `<img src="http://www.law.go.kr/flDownload.do?...">`가 **3건** 박혀 있다(한자 이미지). 제거 필요

### 골든셋(D-007)에 미치는 영향

- **질문 6은 정답 청크가 복수다.** 광견병 접종을 직접 의무화한 조문이 없다 → 골든셋 스키마가 정답 ID를 여러 개 받아야 한다

### 도메인 무관 조문을 거를 것인가

가축전염병 예방법 조문 중 반려견 관련은 광견병 몇 조뿐이고, 별표 최대 항목(검역시행장 시설기준 52,862자)은 축산 농가용이다. **필터를 두지 않고 전부 인덱싱하되 `subcategory`로 구분한다** — 필터 규칙을 잘못 짜면 조용히 정답이 사라지고, 코퍼스가 작아 용량 문제가 없다.

### 재개 조건 (확정을 뒤집으려면)

확정은 "논의 종료"가 아니라 "코드 명세로 승격"이다. 아래 중 하나가 관측되면 해당 항목만 재개한다.
- 3단계 검문소①에서 질문 1~7의 정답 청크가 **하나라도 안 만들어지면** → 재개
- 6단계에서 무관 조문(축산 농가용 별표 등)이 top-5를 오염시키면 → **도메인 필터 항목만** 재개
- 8단계 top-5 육안 확인에서 잘린 청크가 보이면 → 해당 단위 재개

## D-007. 품질 평가 체계 및 자동화 — 🔶 제안 (2026-08-19 논의)

**원칙: 검색 평가(결정적·저비용)와 생성 평가(LLM judge·고비용)를 분리하고 검색부터 조인다.** RAG 실패 대부분은 검색 실패.

**골든셋** (`data/eval/golden_v1.jsonl`, git 관리)
- 정답 단위 = **(문서 ID + 조항번호 section)**. 청크 ID로 잡으면 청킹 변경 시 전량 무효 — 평가 시점에 청크로 매핑해 청킹 실험에도 골든셋 불변
- 도메인당 6~10개, 총 40~60(v1). 질문 유형 배분: ① 사실 단답 ② 구어 패러프레이즈(dense 테스트) ③ 정확 용어·조문(lexical 테스트) ④ 조건 복합(메타필터 테스트) ⑤ 멀티 문서 ⑥ **무답 질문**(abstention 테스트)
- LLM 보조 생성 시 표면 중복 편향 주의("문서 어휘 쓰지 말 것" 지시) + 사람 검수 필수

**검색 지표** — 주력 **Hit Rate@5**(k는 생성 투입 개수와 일치) + **MRR**(순위 민감 → 리랭커 효과 판정기, D-003 도입 여부를 이 지표로 결정). nDCG는 이진 라벨이라 v1 스킵. **보고는 전체 평균 + 도메인×질문유형 슬라이스 필수** (평균에 숨는 실패 검출)

**LLM-as-a-judge** (루브릭 4종, rationale→verdict 순서의 JSON, temperature 0)
1. Faithfulness — 답의 주장 분해 후 컨텍스트 근거 확인 (환각 검출)
2. **인용 정확도(1번 KPI) — 3단 반자동**: 정규식으로 인용 추출 → DB 실존 검증(rule, judge 불필요) → 해당 조항이 주장을 지지하는지만 judge
3. 답변 정확성 (참조 답안 대비)  4. Abstention (무답 질문에 정직한 "규정 없음")
- judge 위생: 생성·judge 모델 급 분리(예: flash 생성 → pro judge) / **사람 라벨 30개와 일치율로 judge 캘리브레이션 후 신뢰** / judge 프롬프트·모델 버전 고정, 변경 시 재캘리브레이션

**자동화**
- `python -m eval run --config exp.yaml` → `results/{run_id}.json` + report.md (git 커밋). 기록 = git sha + 코퍼스 스냅샷 + config + 전 지표 (재현성 삼각형)
- 회귀 게이트 2단: **smoke**(고정 미니 코퍼스, 검색 지표만, CI/PR마다 수 분) + **full**(전체 코퍼스 + judge, 수동·야간)
- 운영 연동: 재적재 완료 → Celery chain으로 검색 eval 자동 실행 → baseline 대비 Hit@5 3%p 하락 시 알림, 관리자페이지에 지표 트렌드
- 도구: ragas/deepeval 참고만 하고 자체 구현 (지표 특수성 — 인용 정확도 — 및 투명성)

## D-008. 데이터 저장 규약 및 documents 스키마 정정 — ✅ 확정 (2026-08-19)

**배경** — `data/README.md`(저장 규칙)와 `db/init/01_schema.sql`(스키마)을 대조하니 어긋난 지점이 여럿이었다.
main에서 별도로 진행된 스키마 검토 결과를 이 브랜치 규약과 합치면서 아래 9건을 확정한다.
데이터 적재 전이므로 스키마는 `DROP TABLE documents CASCADE;` 후 `01` → `02` 재실행으로 반영한다.

### 1) 원본은 git에 커밋하지 않는다 — 기존 방침 변경

> ⚠️ **이 항목의 "`.meta.json`만 커밋" 부분은 D-017 에서 뒤집혔다.** meta 도 커밋하지 않는다.
> 원본을 커밋하지 않는다는 결정 자체는 유효하다.

`raw/`의 원본(pdf/html/xml/json)과 `processed/` 전체를 gitignore하고, **`.meta.json`만 커밋**한다.

- 이 레포는 public이다. 정부 자료는 공공누리로 재배포되지만 **펫보험 약관은 보험사 저작물**이라 리스크가 있다 (시드에 insurance 3건)
- D-007이 요구하는 "코퍼스 스냅샷"은 `.meta.json`의 `source_url`+`sha256`+`fetched_at`으로 충족된다. 원본 바이트 자체가 필요한 게 아니다
- 기존의 "파일당 100MB 금지" 규칙은 원본 커밋을 전제한 것이라 함께 폐기

**수용하는 트레이드오프** — 공고문이 내려가면 원본 재취득이 불가능하다. 로컬 `raw/`를 보존 대상으로 취급한다.

### 2) `.meta.json`과 크롤 로그는 역할이 다르다 — 둘 다 유지

`.meta.json` = 문서의 **출처 정보**(인덱싱 게이트) / `manifests/crawl_log.jsonl` = **실행 이력**(재실행 판단).
사이드카만으로는 404·타임아웃을 기록할 곳이 없다(파일이 안 생기므로 meta도 없음) → 죽은 URL을 매번 재시도하게 된다.
JSONL인 이유는 배열과 달리 크롤 중단 시 파일이 깨지지 않아서다.

층위 구분: `crawl_log.jsonl`은 **문서 단위**, D-001 원칙3의 `crawl_runs` 테이블은 **실행 단위**(관리자페이지용).

### 3) `category`에서 `care`·`emergency` 제외

`CHECK (category IN ('policy','travel','food'))`.
진단 성격이 강해 별도 에이전트로 분리한다. `emergency`(응급처치·중독)도 `care`보다 의료적이라 같이 뺐다.
이 레포의 파트는 제도·문서형이다. 필요해지면 제약만 교체하면 되고, 에이전트가 달라도 테이블을 나눌 필요는 없다(category 필터로 격리).

**"예방접종 스케줄 → care" 매핑은 폐기.** `policy` + `trust_level: guideline`으로 대체한다 —
`guideline`은 원래 "접종 스케줄처럼 법정 근거가 없는 문서" 구분용으로 만든 등급이라 역할이 겹쳤다.

### 4) 신뢰 등급은 `trust_level` 유지 (`law` > `official` > `guideline`)

main 검토안의 `authority`(official/expert/community)보다 이 도메인에 정확하다.
**법령 원문과 기관 안내페이지를 구분**하는 것이 조항 인용 KPI에 직결되는데 3단계 안은 둘을 뭉갠다.
블로그·유튜브 도입 시 `community`를 추가한다.

### 5) `source_type`은 매체 축으로 통일 — `pdf` → `document`

`CHECK (source_type IN ('document','web','api','manual'))`.
기존 값은 포맷 축(`pdf`)과 수집 채널 축(`web`,`api`)이 섞여 "웹에서 받은 PDF"의 답이 없었고,
지금 타깃인 정부 공고문이 정확히 그 케이스다. 세부 포맷은 `metadata.format`(`pdf|hwp|hwpx|html|xml|json`)이 담당한다.

`video`/`audio`는 넣지 않는다 — 현재 시드 30개에 영상·음성 소스가 없다. 실제 수집 시 추가.
포맷을 CHECK가 아니라 metadata에 둔 이유: 포맷은 계속 늘어나(xlsx, pptx…) 그때마다 ALTER가 필요해진다.
`WHERE metadata @> '{"format":"hwp"}'` 는 기존 GIN 인덱스로 처리된다.

### 6) `documents.content_hash` 컬럼 신설

`content_hash CHAR(64) NOT NULL UNIQUE` — 청크 텍스트의 SHA-256. `ON CONFLICT (content_hash) DO NOTHING`으로 멱등 적재.
기존 스키마에는 중복을 막을 키가 없어 로더를 두 번 돌리면 행이 2배가 됐다.
NOT NULL이 필수인 이유: SQL에서 NULL끼리는 중복으로 취급되지 않아 해시가 비면 방어가 조용히 뚫린다.
metadata에 넣지 않은 이유: JSONB는 NOT NULL·타입을 강제할 수 없고 `\d documents`에도 안 보인다.

**D-001 원칙2의 해시와 층위가 다르다** — 원본 문서 해시(`.meta.json`)는 재파싱·재임베딩 스킵 판단,
청크 해시(이 컬럼)는 중복 적재 방지. 둘 다 필요하다.

### 7) `subcategory` 표기는 kebab-case, 값은 수집하면서 늘린다

CHECK 제약 없음. `raw/` 하위 폴더명과 표기를 맞춘다(`leash-muzzle`).
값 사전은 "확정 목록"이 아니라 **"지금까지 쓴 값의 기록"** 으로 운용한다 —
실제 문서를 보기 전에 짠 분류는 대개 어긋나고, 재분류는 `UPDATE` 한 줄이며 `content`가 안 바뀌므로 **임베딩 재계산이 불필요**하다.

### 8) 가공 산출물은 단계별로 분리

`processed/` 를 `parsed/`(텍스트 추출) → `chunks/`(청킹) → `embeddings/`(벡터)로 나눈다.
파서를 교체하면 `parsed/`부터, 청크 크기를 바꾸면 `chunks/`부터만 다시 돌리면 되고 크롤링은 재실행하지 않는다.
**D-006의 "구조 파싱 성공률"·"스캔 PDF 비율"은 `parsed/` 산출물이 따로 남아야 측정 가능하다.**
포맷은 jsonl(디버깅·diff 용이), 1024차원 벡터만 parquet.

### 9) 대량 문서 소스의 파일명 보완

기본은 기존 규칙 `{slug}__{YYYYMMDD}.{ext}`.
지자체 공고처럼 한 소스에서 문서가 수십 개 쏟아져 slug를 개별 부여할 수 없는 경우
`{source_id}__{YYYYMMDD}__{urlhash8}.{ext}` (`urlhash8` = `sha256(url)[:8]`)를 쓴다.
원래 파일명을 못 쓰는 이유: 공공기관 첨부는 `공고문.pdf`·`붙임1.pdf` 처럼 겹쳐 덮어쓰고,
URL에 한글·쿼리스트링이 섞여 Windows 경로로 부적합하다.

**미결 (이 결정에 포함하지 않음)** — PDF 파서 선택(pypdf/pdfplumber/PyMuPDF)은 후보와 판단 재료만
`data/README.md`에 정리해두고 파싱 단계 착수 시 결정한다. PyMuPDF의 AGPL-3.0이 변수.

## D-009. 크롤러 패키지 배치와 소스 모듈 계약 — ✅ 확정 (2026-08-19)

**배치** — `backend/crawler/`. `backend/` 는 FastAPI 폴더가 아니라 uv 프로젝트 하나이고, FastAPI(`app/`, 이동 예정)·`crawler/`·`pipeline/`(예정)·`tasks/`(Phase 3) 가 그 안의 형제 패키지다.
D-001 "FastAPI 백엔드와 같은 코드베이스/이미지" 의 구체화. 레포 루트에 별도 프로젝트로 두면 venv·lock 2개 + 공유 코드(설정·DB 모델·임베딩)용 세 번째 패키지가 필요해져 혼자 하는 파트 레포에서 과함.

**의존 방향** — `app → crawler`, `tasks → crawler` 한쪽뿐. `crawler` 는 `app`/`tasks` 를 import 하지 않는다 → FastAPI 없이 `python -m crawler` 단독 실행 (D-001 원칙 1).

**의존성 그룹** — 크롤러 의존성(httpx·bs4·lxml·pyyaml·tzdata)은 메인 `dependencies`. `ml` 그룹처럼 분리하지 않는 이유: 가볍고, Celery 워커·관리자 API 가 같은 이미지에서 crawler 를 import 하므로 기본 `uv sync` 에 포함되어야 한다. 그룹 분리는 OCR 엔진·HWP 파서처럼 무겁거나 설치가 까다로운 것이 들어올 때.

**소스 모듈 계약** — 소스 하나 = 모듈 하나 (`sources/{id}.py`, yaml id 의 `-` → `_`). 책임은 `discover()`(URL+slug 목록) 와 `extract()`(제목·본문·published_at·cites) 둘뿐. 받기·저장·로그·변경 감지·예절(UA, 1.5s 간격, robots, 재시도)은 `core/` 가 한다. 소스가 23개가 되어도 각 모듈은 site-specific 지식만 가진다.

**변경 감지 지문** — html 은 `extract().text` 의 sha256, 그 외는 원본 바이트. 조회수·세션값 때문에 바이트 해시는 매번 changed 가 뜬다 (data/README.md 규칙 3 갱신).

**첫 사이클 결과 (easylaw-pet)** — 본문 7 + 100문100답 7 = 14건. 시드 URL 이 '페이지 오류' 를 반환해 정정(`status: verified` 는 조사 시점 기준일 뿐). 100문100답 탭(`&menuType=onhunqna`) 은 Q/A + 관련법령 구조라 D-007 골든셋 재료로 적합. 카드뉴스는 이미지라 제외. 본문 인용 조항을 D-004 형식(`제16조제2항제1호`)으로 `cites` 에 보존 — 해설(`official`) → 법령(`law`) 연결고리.

## D-010. 원본 부재 시 재수집 (meta-raw 불일치 복구) — ✅ 확정 (2026-08-20)

**문제** — meta 와 원본이 어긋나면(meta 는 있는데 원본이 없음) `sha256` 이 같아 **전부 `same` 으로 스킵**되고 원본이 한 건도 안 남는다. 파싱·청킹 단계가 빈손이 된다. 실제로 8/19→8/20 사이 PC 를 옮기며 겪었고, `--force` 로 우회했다.

> **당시 원인은 D-017 로 사라졌다** — 그때는 `.meta.json` 만 커밋되고 원본은 미추적이라 clone 직후 반드시 이 상태가 됐다. 지금은 meta 도 커밋하지 않으므로 clone 직후에는 meta 자체가 없어 그냥 전부 `NEW` 로 받는다.
> 그래도 이 규칙은 유지한다. `data/` 를 PC 사이에 복사하거나 용량 때문에 원본만 지우는 등 **어긋남은 여전히 생길 수 있고**, 그때 조용히 스킵되는 것이 가장 나쁜 실패다.

**결정** — `Store.save()` 의 변경 감지에 조건을 하나 더 둔다: sha256 이 같아도 **meta 가 가리키는 `raw_file` 이 디스크에 없으면 다시 받아 저장**한다.

```
changed = force  or  raw_missing  or  prev_sha != fingerprint
```

**근거** — `.meta.json` 은 "이 문서를 받은 적이 있다"는 **기록**이고, 파이프라인이 실제로 소비하는 것은 **원본 파일**이다. 둘이 어긋난 상태(meta 있음 + raw 없음)는 정상 상태가 아니라 복구 대상이다. 변경 감지의 목적은 "불필요한 재파싱·재임베딩 방지"(D-001 원칙 2)이지 "원본이 없는데도 안 받기" 가 아니다.

**`--force` 와의 차이** — `--force` 는 sha 가 같아도 새 날짜로 무조건 다시 쓰는 수동 스위치라 매번 중복 원본이 쌓인다. 이 로직은 **없을 때만** 받으므로 clone 직후 1회만 동작하고 이후에는 다시 `same` 이 된다. 사람이 상황을 알아채고 플래그를 붙여야 했던 것을 기본 동작으로 내린 것.

**관측 가능성** — `StoreResult.reason` 을 추가해 `new` / `changed` / `raw-missing` / `forced` / `same` 을 구분하고, CLI 라벨(`RAW-MISSING`)과 `crawl_log.jsonl` 의 `reason` 필드에 같은 값을 쓴다. `changed:true` 만 봐서는 내용이 바뀐 것인지 원본이 없었던 것인지 구분되지 않아, 로그로 사후 분석이 안 된다.

**부수 효과 (의도됨)** — 복구분은 오늘 날짜로 저장되므로 파일명 날짜가 원 수집일과 달라진다. 실제 수집 시각은 meta 의 `fetched_at` 이 정확하고, `previous_sha256` 이 같으므로 내용이 그대로임은 추적 가능하다.

**적용 범위** — `core/store.py` 한 곳. 소스 모듈은 변경 없음 (D-009 계약대로 변경 감지는 `core/` 책임).

## D-011. 법령 원문은 `lsInfoR.do` 웹 원문으로 먼저 받는다 — ✅ 확정 (2026-08-20)

**배경** — §1 계획은 "법령은 조문 단위 구조화 데이터(API)로 수집, 웹 스크래핑은 API 발급 전 임시" 였다. LAW_OC 미발급 상태에서 웹 원문을 정찰해 보니 전제가 바뀌었다.

| 요소 | 내용 |
|---|---|
| `#conTop` | `동물보호법 [시행 2026. 7. 7.] [법률 제21839호, 2026. 7. 7., 일부개정]` — 법령명·시행일·공포번호·개정구분 |

**지문에서 제외한 것** — `.cont_subtit`(소관부처 연락처 412자, 조직개편만으로 지문이 바뀜), `.byl_pop`(별표 파일 저장 레이어 — 같은 제목을 .hwp/.hwpx/.pdf 로 4번 반복 + "닫힘"), `.rule_area`(위임행정규칙 안내 박스), 조문 앞 `<input type=checkbox>`. 별표 **목록**(`#arDivArea`)은 남긴다 — 어떤 별표가 있는지는 본문 정보다.

## D-012. 소스 모듈을 도메인별로 나누고, API 키를 다루는 규칙을 정한다 — ✅ 확정 (2026-08-20)

### 1) `sources/{domain}/{id}.py` — 도메인이 폴더가 된다

소스가 23개가 되면 `sources/` 가 평평한 `.py` 더미가 된다. **yaml 의 `domain` 을 폴더로 쓴다.**

새 축을 만들지 않은 것이 핵심이다. `domain` 은 이미 yaml 에 있고 `data/raw/{domain}/` 저장 위치와 같은 축이라, 코드 폴더와 데이터 폴더가 저절로 같은 모양이 된다. 분류 기준을 새로 정의했다면 "이 소스는 어느 폴더냐"를 매번 판단해야 했을 것이다.

`registry` 는 `(domain, id) → crawler.sources.{domain}.{id}` 로 **경로를 계산한다**. 폴더를 스캔해 `Source` 하위 클래스를 모으는 방식을 쓰지 않는 이유 — 스캔은 소스가 늘수록 느려지고, import 부작용 순서에 의존하며, 오타가 나면 "그냥 안 잡히는" 조용한 실패가 된다. 계산 방식은 어긋나면 모듈 경로를 찍어 주며 즉시 실패한다.

**레이어는 셋이다.** ① `core/` = 사이트를 모르는 공통(받기·저장·변경감지·텍스트·키 마스킹), ② `sources/{domain}/_*.py` = 사이트 하나의 구조, ③ `sources/{domain}/{id}.py` = 그 사이트에서 무엇을 받을지. 소스가 늘 때 새로 쓰는 코드는 ③뿐이어야 한다. 같은 사이트를 두 번째로 건드리면 ②를 만들고(`_lawgokr`), 사이트가 달라도 반복되면 ①로 올린다(`textutil`).

`realtime` 도메인은 저장하지 않고 API 직조회라 소스 모듈이 생기지 않는다.

### 2) API 키는 `.env` → `config` → **URL 마스킹**

`.meta.json` 은 git 에 커밋된다(D-008). 그런데 API 소스는 키를 쿼리스트링에 넣으므로, 그 URL 이 `source_url` 로 들어가면 **키가 그대로 공개 저장소에 올라간다.** 첫 API 소스를 만들면서 확정한다:

- `core/config.py` 가 레포 루트 `.env` 를 읽는다 (10줄, python-dotenv 안 씀 — crawler 의존성을 얇게 유지, D-009). 이미 있는 환경변수는 덮지 않는다
- `config.redact(url)` 을 **저장·로그·화면 출력 직전 모든 지점**에 건다 (`store.save` 의 `source_url`, `store.log` 의 `url`, CLI 의 오류 출력)
- 마스킹은 두 겹이다. **파라미터 이름**(`OC=`, `serviceKey=` …)으로 한 번, **발급받은 값 자체**로 한 번. 이름만 쓰면 규격이 다른 새 API 를 놓치고, 값만 쓰면 `LAW_OC` 처럼 짧은 값(이메일 앞부분)이 URL 의 멀쩡한 부분을 오탐한다. 값 매칭은 8자 이상일 때만 건다
- 키 미설정 시 소스는 `discover()` 에서 **발급처를 알려주며** 멈춘다. 빈 키로 호출해 401 을 받는 것보다 낫다

### 3) `Target.meta["subcategory"]` 로 문서별 분류를 덮어쓴다

`law-drf-api` 하나가 동물보호법·가축전염병예방법·수의사법·자연공원법을 받는다. 소스 클래스 속성은 소스당 하나라 문서별 분류를 담을 수 없었다. `store.save` 가 `target.meta["subcategory"] or src.subcategory` 로 읽는다 — `document_title` 이 이미 쓰던 방식과 같다.

### 4) 인용 파싱은 줄바꿈에서 끊는다 (버그 수정)

`textutil.cites()` 가 `re.S` 로 줄을 넘어 매칭하고 있었다. 종결부호 없이 줄이 끝나면 **다음 줄의 조문 번호까지 앞 법령의 인용으로 빨아들인다** — `「수의사법」 제10조제2항에 따라 …` 다음 줄이 `제15조(등록대상동물의 등록 등)` 이면 `수의사법 제15조` 라는 없는 인용이 만들어진다.

법령 원문 6건에서 **허위 인용 19건**이 나왔다(동물보호법 시행규칙 10, 시행령 5, 가축전염병 시행규칙 3, 법 1). easylaw-pet 14건은 영향 없음(저장된 meta 와 대조 확인). "출처 링크 + 조항 번호 인용" 이 KPI 라 **없는 인용을 만드는 것이 못 찾는 것보다 나쁘다.**

수정 후 `--force` 로 법령 6건 meta 를 재생성했다(같은 날짜라 파일명이 같아 제자리 갱신). 여기서 드러난 한계 — **`.meta.json` 은 원본이 바뀔 때만 다시 쓰이므로, meta 를 만드는 로직을 고쳐도 기존 meta 는 옛 값 그대로다.** 지금은 `--force` 로 수동 해결한다. 소스가 많아지면 "meta 스키마·추출 버전" 필드를 두고 버전이 다르면 재생성하는 방식을 검토한다.

### 5) `law-drf-api` — 규격은 검증했고, 실제 수집만 보류

**정정 (2026-08-20 같은 날)** — 처음에 "DRF 는 OC 만으로 안 되고 서버 IP/도메인 등록이 필수" 라고 적었으나 **틀렸다.** 근거가 가짜 OC(`testkey123`)로 호출했을 때의 응답 하나뿐이었는데, 그 상황은 OC 자체가 없어서 실패한 것이라 IP 등록 여부를 말해 주지 않는다. 응답의 "IP주소 및 도메인주소를 등록해 주세요" 는 **원인을 특정하지 않는 공통 안내문**이다. 법제처 공식 매뉴얼이 공개한 샘플 키 `OC=test` 가 아무 등록 없이 이 PC 에서 그대로 동작하는 것으로 확인했다. **IP/도메인 등록은 필요 없다.**

## D-014. env 파일 배치와 의존 방향 가드 — ✅ 확정 (2026-08-20)

### 1) env 경계는 "런타임 단위"다 — `backend/.env` 하나

기존 관례("각 프로젝트 최상단에 그 프로젝트가 쓰는 `.env`")를 따른다. 관건은 **여기서 프로젝트를 몇 개로 세느냐**인데, `backend/` 는 사람이 보기엔 crawler(순수 py) + FastAPI 둘이 합쳐진 느낌이지만 **배포 단위는 하나**다 — D-001 에서 크롤러는 FastAPI 와 같은 이미지에 싣기로 했고, Celery 워커가 `crawler` 를 import 해서 태스크를 돌린다.

| 런타임 단위 | 프로세스 | env |
|---|---|---|
| backend 이미지 | FastAPI · Celery worker · beat · `python -m crawler` | `backend/.env` |
| frontend 이미지 | Next.js | `frontend/.env` |
| 인프라 | postgres, redis | 루트 `.env` (compose 가 읽는다) |

`crawler/.env` 를 따로 두지 않는 이유 — Celery 워커는 크롤러와 앱을 다 import 하므로 어차피 두 파일을 다 읽어야 한다. 노출 범위는 안 줄고 관리할 파일만 는다.

**변수마다 집은 하나다.** 루트 = 인프라가 *만드는* 값(`POSTGRES_*`), `backend/.env` = 백엔드가 *쓰는* 값(API 키). DB 접속정보는 루트에만 두고 compose 가 `DATABASE_URL` 로 조립해 내려준다. 같은 값을 두 파일에 적으면 한쪽만 고쳐서 어긋난다.

`env_file: ./backend/.env` 는 안전하다 — 위험한 건 **모든 서비스가 루트 `.env` 하나를 통째로 보는** 구성이다(프론트 컨테이너가 `POSTGRES_PASSWORD` 와 `LAW_OC` 까지 받게 된다). 파일을 배포 단위별로 나누면 그 문제가 구조적으로 막힌다.

`.gitignore` 는 손댈 필요가 없다 — `.env` · `.env.*` 는 슬래시가 없어 모든 하위 경로에 적용되고 `!.env.example` 도 마찬가지다.

### 2) 읽는 순서와 `REPO_ROOT` 선택화 (컨테이너 import 크래시 수정)

**우선순위: 실제 환경변수 > `backend/.env` > 루트 `.env`** (`setdefault` 라 먼저 읽은 쪽이 이긴다). 배포에서는 오케스트레이터가 넣은 값이 항상 이기므로 두 파일이 없어도 그대로 돈다.

기준점은 `PACKAGE_ROOT = config.py 에서 세 단계 위` = `backend/`. 레포를 통째로 두든 `backend/` 만 이미지에 넣든 **항상 존재하는** 유일한 경로다.

이 과정에서 배포를 막는 버그를 하나 잡았다. `_find_repo_root()` 가 `data/manifests/seed_sources.yaml` 을 못 찾으면 예외를 냈는데, 그게 **모듈 import 시점**이었다. 백엔드 이미지에는 `data/` 가 없고 `app → crawler` (D-009) 라 **FastAPI 를 import 하는 순간 컨테이너가 안 뜬다.** 재현 결과:

| 상황 | 수정 전 | 수정 후 |
|---|---|---|
| `data/` 없이 import | 💥 크래시 | ✅ 통과 (`REPO_ROOT=None`) |
| `DAENGS_DATA_DIR` 만 지정 | 💥 여전히 크래시 | ✅ 통과 |
| 데이터가 실제로 필요한 시점 | — | ✅ 무엇을 설정해야 하는지 안내하며 실패 |

`REPO_ROOT` 는 `.env` 경로에만 필요한데 조건 없이 먼저 계산하고 있었다. 이제 `Path | None` 이고, `data/` 를 처음 건드리는 두 지점(`registry.load_seeds()`, `Store.__init__`)에서 `require_data_dir()` 이 검사한다. 배포 시 `DAENGS_DATA_DIR=/data` + 볼륨 마운트 하나로 끝난다.

### 3) 의존 방향을 사람이 아니라 기계가 지킨다

`app → crawler` 한 방향(D-009)은 지금까지 **사람이 지키는 규칙**이었다. 한 번 뒤집히면 크롤러가 앱 설정·DB 세션을 끌고 들어와 CLI 도 워커도 앱 전체를 세워야 돌아간다(D-001 원칙 1 위반).

`backend/tests/test_import_direction.py` 가 `crawler/**/*.py` 의 import 문을 **AST 로 정적 검사**한다. 실제로 import 해서 `sys.modules` 를 보는 방식은 함수 안에 숨은 import 를 놓치고 테스트 프로세스 상태에 영향을 받는다.

테스트가 2개인 이유 — 하나는 위반을 검사하고, 다른 하나는 **검사기 자체가 살아 있는지** 확인한다(일부러 위반 파일을 만들어 잡히는지 본다). 이게 없으면 검사기가 조용히 아무것도 안 보게 돼도 테스트는 계속 통과한다. 실제 `crawler/core/` 에 위반 파일을 넣어 잡히는 것까지 확인했다.

`pytest` 는 `dev` 그룹에 추가했다 (`uv sync --group dev`, 실행은 `uv run pytest`). 런타임 의존성은 그대로 얇다.

### 4) 진짜로 쪼갤 시점

지금 합쳐 두는 것이 맞지만, 다음 중 하나가 오면 이미지를 분리한다 — **크롤러에만 무겁거나 설치가 까다로운 의존성**(HWP 파서·OCR)이 필요해질 때, 또는 **크롤러만 스케일·스케줄이 달라질 때**. 그때도 레포는 하나로 두고 `uv sync --group crawl` 로 이미지만 나눈다. D-009 가 잡아 둔 의존성 그룹 분리 기준과 같다.

**compose 에 backend 서비스를 추가하는 것은 이번 범위 밖이다** (지금은 db 만 있다).

## D-015. crawler 설정은 pydantic-settings 로 읽는다 — ✅ 확정 (2026-08-20)

**배경** — D-014 에서 `.env` 로더를 10줄짜리 손 파서로 넣었다. 근거를 세 개 댔는데 전부 틀렸다.

| 당시 근거 | 실제 |
|---|---|
| "python-dotenv 를 새로 넣지 않으려고" | `python-dotenv` 는 `pydantic-settings` 의 **필수** 의존성이라 이미 설치돼 있었다 |
| "pydantic-settings 는 app 쪽 관심사" (config.py 원 주석) | 라이브러리일 뿐이다. crawler 가 app 을 import 하는 게 아니라 D-009 와 무관하다 |
| "필요한 건 10줄뿐" | 그 10줄이 조용히 틀린다 (아래) |

**손 파서가 깨지던 지점** — 값이 틀려도 예외가 안 나서 **키가 잘못된 채로 API 를 호출**하게 된다.

| `.env` 원문 | pydantic-settings | 손 파서 |
|---|---|---|
| `LAW_OC=abc123 # 8/20 발급` | `'abc123'` | `'abc123 # 8/20 발급'` ❌ |
| `export LAW_OC=v` | `'v'` | 키가 `'export LAW_OC'` 이 되어 영영 못 찾음 ❌ |

**결정** — `crawler/core/config.py` 에 `Settings(BaseSettings)` 를 두고 값을 전부 필드로 선언한다. 크롤 예절 상수(UA·요청 간격·타임아웃·재시도)도 필드로 올려 환경변수로 조절할 수 있게 했다.

**우선순위는 그대로** 실제 환경변수 > `backend/.env` > 루트 `.env`. `env_file` 에 튜플로 넘기면 **뒤쪽이 우선이고 둘이 병합된다** — 루트에만 있는 값도 그대로 올라온다(실측 확인). 없는 파일은 알아서 건너뛴다.

**`DAENGS_REPO_ROOT` 만 `os.environ` 에서 직접 읽는다.** 어느 `.env` 를 읽을지 정하려면 이 값이 먼저 필요해 Settings 안에 둘 수 없다(닭-달걀). 컨테이너 레벨 노브라 성격도 맞는다. `DAENGS_DATA_DIR` 은 env 파일 선택에 영향을 주지 않으므로 Settings 필드다.

**모듈 상수는 유지한다** — `config.RAW_DIR`·`SEED_FILE`·`USER_AGENT` 등을 `settings` 에서 파생시켰다. 호출부(store·registry·fetch)를 건드리지 않아 이번 변경의 위험 범위가 config.py 한 파일로 묶인다. `redact()`·`require_data_dir()` 도 그대로다.

**crawler 는 자기 Settings 를 가진다.** app 이 생기면 app 이 같은 `backend/.env` 를 자기 Settings 로 읽는다. 공유 Settings 를 만들면 크롤러가 `DATABASE_URL`·`GEMINI_API_KEY` 까지 알게 되어 `app → crawler` 한 방향(D-009)이 흐려진다. env **파일**은 배포 단위 단위로 공유하고(D-014), **Settings 클래스**는 패키지별로 나눈다.

**테스트** — `tests/test_config_env.py` 7개. 우선순위 두 종류, 주석·export·따옴표 파싱, 없는 파일, 마스킹(파라미터명/값/무관 URL), `require_data_dir()` 안내, 레포 밖 `_find_repo_root() is None`. pytest 가 `crawler` 를 import 할 수 있도록 `[tool.pytest.ini_options] pythonpath = ["."]` 을 pyproject 에 넣었다.

| 동물보호법 시행령 | 2026-06-03 | **2025-06-02** ✗ (= 공포일자) |
| 동물보호법 시행규칙 | 2026-06-03 | **2025-08-07** ✗ (= 공포일자) |

원인 — **한 번 공포에 단계별 시행일이 걸린 법령**이다. `target=eflaw` 이력을 보면 동물보호법 시행령은 같은 법령일련번호(271385)가 시행일자 20250602 / 20251203 / 20260603 으로 **세 번** 나온다. 본문조회는 그중 기준 레코드 날짜를 주고, 오늘 시행 중인 날짜(20260603)는 **목록조회의 `현행연혁코드=현행` 레코드**에만 있다. `MST` 로 바꿔도, `efYd` 를 붙여도 응답이 동일해 본문조회로는 얻을 수 없다.

**결정** — `published_at` 은 `discover()` 의 목록조회에서 받아 `Target.meta` 로 넘긴다. 본문조회 값과 다르면 `record_date` 로 남겨 어느 쪽을 썼는지 추적 가능하게 한다.

**본문 자체는 같은 버전이다** — 조문 집합을 웹 원문과 대조해 확인했다(시행령 45/45, 시행규칙 79/79, 양쪽에만 있는 조문 0). 시행규칙 제2조 맹견 5종도 동일. 틀린 것은 날짜 **필드 하나**뿐이었다.

`법령일련번호` 를 `law_serial` 로 함께 저장한다 — **웹 원문의 `lsiSeq` 와 같은 값**이라(287795·271385·273181 …) 두 소스의 같은 문서를 맞춰 볼 수 있다.

### 2) 별표 본문이 API 에 통째로 있다 (D-011 미해결 해소)

D-011 에서 "별표·별지서식의 내용이 웹 HTML 에 없다(과태료 부과기준 등)" 를 미해결로 남겼다. API 본문조회의 `<별표단위>` 에는 파일 링크뿐 아니라 **`<별표내용>` 에 텍스트가 그대로 들어 있다.** 동물보호법 시행규칙 80개, 가축전염병 예방법 시행규칙 106개 전부 내용이 있다(별표 하나가 2,000~4,000자).

**부칙(`<부칙단위>`)도 함께 넣는다** — 시행일과 경과규정이 들어 있고, 웹 원문(D-011)이 본문에 포함하므로 두 소스의 범위를 맞춘다.

그 결과 추출 텍스트가 크게 늘었다 (동물보호법 시행규칙 34,400자 → 252,205자). HWP 파서 없이 별표를 확보했으므로 **D-004 파싱 단계에서 PDF/HWP 파서 결정을 법령 도메인에는 미뤄도 된다.**

### 3) 검증한 것

- **키 마스킹** — `.meta.json` 8건의 `source_url` 이 전부 `OC=***`. `data/` 전체를 키 문자열로 훑어 0건 확인. (`config.py` 가 걸리는 것은 User-Agent 의 이메일 앞부분이 OC 와 같기 때문이다 — DRF 의 OC 가 곧 이메일 ID 라 원래 semi-public 이고, 우리가 흘린 값이 아니다. 그래도 `OC=` 가 붙은 URL 은 그대로 재사용 가능하므로 마스킹은 유효하다.)
- **응답 바이트 안정성** — 재실행 시 8/8 `same`. xml 지문을 원본 바이트 해시로 두는 D-009 규칙을 그대로 유지한다.
- **IP/도메인 등록 불필요** — D-012 의 정정대로, 등록 없이 정상 동작했다.

## D-017. `.meta.json` 도 커밋하지 않는다 — ✅ 확정 (2026-08-20, D-008 규칙 1 일부 뒤집음)

**결정** — `data/` 의 **수집 결과물은 어느 것도 git 에 올리지 않는다.** 원본·`.meta.json`·`crawl_log.jsonl`·`processed/` 전부 로컬이다. 추적하는 것은 **무엇을 받을지**(`seed_sources.yaml`)와 **폴더 구조**(`.gitkeep`) 뿐이다. (`eval/`·`reference/` 는 손으로 만드는 것이라 성격이 달라 그대로 커밋한다.)

D-008 규칙 1 이 "`.meta.json` 만 커밋" 이라고 했던 부분을 뒤집는다. 원본을 커밋하지 않는다는 결정 자체는 그대로다.

**meta 의 역할이 무엇인지가 기준이다.** meta 는 "이미 받은 것을 또 받지 않기" 위한 **로컬 상태**다. `crawl_log.jsonl` 과 성격이 같고, 그건 처음부터 미추적이었다. 둘을 다르게 취급할 이유가 없다.

**커밋해도 실행에 도움이 안 된다** — 새 clone 에서 meta 를 지우고 크롤러를 돌려 확인했다. seed yaml 과 소스 모듈만 있으면 정상 수집되고(3건 전부 `NEW`), 두 번째 실행부터 `same` 으로 변경 감지가 살아나며, sha256 이 원본 PC 와 3/3 일치했다. meta 가 있든 없든 새 PC 에서는 어차피 원본이 없어 전부 다시 받는다.

**오히려 어긋난 상태를 만들었다** — meta 만 커밋되고 원본은 안 되니 clone 직후 반드시 "meta 는 있는데 원본이 없는" 상태가 됐고, 그것 때문에 D-010 을 만들어야 했다. 원인 자체를 없앤다.

**수집 현황은 어디서 보나** — `docs/data-sources.md` 의 파트별 체크리스트가 담당한다. 원래부터 "사람이 보는 요약" 이었고, meta 는 기계용이었다.

**대신 잃는 것** — 팀원이 clone 만으로 "무엇이 언제 수집됐는지" 를 볼 수 없고, `cites` 정규식을 고쳤을 때처럼 meta diff 로 변화가 드러나던 것도 없어진다. 혼자 쓰는 파트 레포라 수용한다. 필요해지면 되돌리는 것은 `.gitignore` 한 줄이다.

### 운영상 주의 — 상태가 로컬이라는 뜻

변경 감지의 근거가 `data/raw/*/*.meta.json` 이므로 **`data/` 가 사라지면 전부 다시 받는다.** D-001 의 Celery 워커를 컨테이너로 띄울 때 `data/` 는 **반드시 영속 볼륨**이어야 한다. 아니면 관리자 페이지 트리거나 Beat 배치가 돌 때마다 같은 문서를 다시 내려받는다 — 이 결정의 목적("같은 내용 재크롤 방지")이 프로덕션에서만 깨지게 된다.

더 나아가면 크롤 상태를 DB(`crawl_runs` 또는 별도 테이블)로 옮기는 선택지가 있다. 지금은 과하다 — 파일 하나로 되는 일이고, DB 로 옮기면 크롤러가 DB 없이 단독 실행되지 않아 D-001 원칙 1 을 깬다. 워커가 여러 대로 늘어 파일 상태를 공유할 수 없을 때 다시 본다.

### D-010 은 유지한다

발생 원인(clone 직후 meta-only)은 사라졌지만 규칙은 남긴다. `data/` 를 PC 사이에 복사하거나 용량 때문에 원본만 지우는 등 **어긋남은 여전히 생길 수 있고**, 그때 조용히 `same` 으로 스킵되는 것이 가장 나쁜 실패다. 실제로 8/19→8/20 PC 이동에서 `data/` 폴더를 손으로 복사했다.

### 적용

`.gitignore` 에서 `!data/raw/*/*.meta.json` 예외를 지우고, 이미 추적 중이던 meta 28건을 `git rm --cached` 로 해제했다(디스크에는 그대로 남는다). 히스토리에 남는 옛 meta 는 그대로 둔다 — 비밀값이 없고(마스킹 확인 완료, D-016) 히스토리 재작성은 과하다.

## D-018. 인덱싱 패키지 경계와 파서 계층·공통 IR — ✅ 확정 (2026-08-21)

**배경** — 2단계(파서)를 시작하려니 코드를 어디에 둘지부터 정해야 했다. D-009 에서 크롤러를
`backend/crawler/` 로 분리했지만 **파서·청커·임베더·적재·검색이 어디로 갈지는 정한 적이 없다.**
지금 소스는 4곳(법령 API / easylaw 해설 / 법령 웹 원문 2종)이고 앞으로 펫보험 약관 PDF, 지자체 공고
HWP, 보조금24 JSON 이 붙는다. **파싱 전략은 소스마다 다를 수밖에 없다** — 그 차이를 어디에 가둘지가
이 결정의 본론이다.

### 1. 최상위 폴더는 **제품 파트**를, 그 아래가 **단계**를 이름 짓는다

```
backend/                     ← uv 프로젝트 하나 (requires-python 3.12, lock 1개)
├── crawler/     수집        웹 → data/raw          (두 파트 공용)
├── rag/         파트① 엔진  raw → chunks → vectors → DB → 검색
├── realtime/    파트② 엔진  날씨·미세먼지 API 직조회 (미착수)
└── app/         FastAPI     두 엔진을 HTTP 로 노출할 뿐, 로직을 갖지 않는다
```

의존 방향은 **`app → rag → crawler`** 한쪽뿐이다. `rag` 가 `crawler` 를 참조하는 것은
`core/config.py` 의 **data/ 경로 탐색 하나뿐**이고(D-014 의 "경로 탐색은 한 곳"을 유지),
`rag` 는 자기 Settings(`DATABASE_URL`·`GEMINI_API_KEY`·모델명)를 따로 갖는다.
`tests/test_import_direction.py` 의 `FORBIDDEN` 에 `rag` 를 추가해 역방향을 기계가 막는다.

**`rag` 라는 이름이 포괄적인 것은 버그가 아니라 의도다.** 최상위가 이름 짓는 대상이 "단계"였다면
`parse/ chunk/ embed/ load/ search/` 로 5~6개가 늘고 파트②가 붙을 자리가 없다. CLAUDE.md 가 이
레포를 이미 파트 2개로 정의하고 있으므로 그 분해를 그대로 쓴다. 단계는 `rag/` 안에서 말한다.

```
rag/
├── __main__.py   CLI: parse | chunk | embed | load | search   (크롤러와 같은 방식)
├── config.py     Settings — DATABASE_URL, GEMINI_API_KEY, 임베딩 모델명
├── ir.py         ★ 공통 중간 표현 = 모든 파서가 지켜야 할 계약 (아래 3)
├── extract/      ① 포맷 층    pdf.py · hwpx.py · html.py · xml.py
├── parsers/      ② 사이트 층  law/law_drf_api.py · law/easylaw_pet.py …
├── chunkers/     3단계
├── embed.py      4단계   ├ load.py 7단계
└── search.py     8단계
```

### 2. uv 프로젝트는 나누지 않는다 — 패키지와 다른 축이다

논의에서 가장 헷갈렸던 지점이라 명시해 둔다. **둘은 독립된 축이다.**

| | uv 프로젝트 | 파이썬 패키지 |
|---|---|---|
| 실체 | `pyproject.toml` + `uv.lock` + `.venv` 한 세트 | 폴더 하나 + import 이름 |
| 정하는 것 | **파이썬 버전**, 의존성 집합, lock | 코드 구조, import 방향 |
| 현재 | `backend/` **1개** | `crawler/` (+ 이번에 `rag/`) |
| 나누는 비용 | 큼 — lock·venv·CI 가 배수로 | **거의 0 — 폴더 하나** |

**D-001 원칙 1 의 "순수 파이썬 패키지"는 "uv 를 안 쓴다"는 뜻이 아니다.** 오케스트레이터(Celery·
Airflow)에 묶이지 않고 `python -m crawler` 로 단독 실행된다는 뜻이다. 실제 실행 명령도
`uv run python -m crawler run ...` 이다.

uv 프로젝트를 나눠야 할 조건은 셋이고 **지금은 하나도 해당하지 않는다** — ① 파이썬 버전이 달라야 함
② 의존성 충돌 ③ 배포 아티팩트가 완전히 갈림(별도 이미지 + 별도 lock). 무게 차이는
`[dependency-groups]` 가 해결한다(`ml` 그룹이 그 사례). 정말 나눠야 할 때가 오면
`[tool.uv.workspace]` 로 그때 나눈다 — 미리 나누면 lock 을 손으로 맞춰야 한다.

`app/` 을 나중에 따로 두는 것도 **새 uv 프로젝트가 아니라 `backend/app/` 폴더**다.
`test_import_direction.py` 가 `app`·`tasks`·`main` 을 이미 금지 이름으로 예약해 두었다.

### 3. 기각한 근거 하나 — "의존성 무게"는 경계를 못 긋는다

최초에 `rag` 분리 근거로 "torch 를 crawler 의 import 경로 밖에 둔다"를 들었으나 **틀렸다.**
- D-001 의 compose 토폴로지에서 `backend`(FastAPI)와 `worker`(Celery)는 **같은 이미지**를 쓴다
- 8단계 검색은 사용자 질문을 문서와 **같은 모델로** 임베딩해야 한다. 승자가 로컬 모델(D-002 후보 3종은
  전부 로컬)인 이상 **torch 는 서빙 런타임에도 들어온다**

따라서 `ml` 그룹의 효용은 배포 분리가 아니라 **"4단계 전까지 6GB 를 안 받아도 되는" 개발 편의**다.
경계의 근거는 다음 넷으로 다시 세웠다: **이름의 정직성**(`crawler` 안에 임베더가 있으면 이름이 거짓),
**변경 국소성**(D-004 는 재개 조건이 명시된 만큼 앞으로 더 뒤집힌다), **테스트 독립성**(파서는
`raw/` 샘플만으로 네트워크·DB 없이 초 단위 테스트가 되지만 크롤러는 안 된다),
**import 방향**(기계가 검사 가능).

### 4. 파서는 크롤러와 **같은 3층**을 쓴다 — 새로 배울 규약을 만들지 않는다

파싱이 소스마다 다른 것은 정상이다. 통제할 것은 **그 차이가 번지는 범위**다. 축을 둘로 분리한다.

| 축 | 무엇이 다른가 | 개수 | 재사용 |
|---|---|---|---|
| **포맷** | PDF 에서 표를 어떻게 뽑나, HWP 를 어떻게 여나 | 6개로 **수렴**(pdf/hwp/hwpx/html/xml/json) | 소스가 늘어도 안 늘어남 |
| **사이트 구조** | 조문 태그 / `plv2a` 클래스 / 공고문의 `□ 지원대상` 관례 | 소스 수만큼 **선형 증가** | 재사용 불가 — 정상 |

| 층 | 크롤러 | 파서 | 아는 것 |
|---|---|---|---|
| ① 공통 | `core/` | `rag/extract/` | 포맷만. 사이트를 모른다 |
| ② 사이트 | `sources/{domain}/_lawgokr.py` | `rag/parsers/{domain}/_*.py` | 사이트 하나의 구조 |
| ③ 대상 | `sources/{domain}/{id}.py` | `rag/parsers/{domain}/{id}.py` | 그 사이트에서 무엇을 뽑을지 |

**디스패치도 스캔하지 않고 계산한다**(D-009 와 동일). 크롤러는 `seed_sources.yaml` 의
`domain`+`id` 로, 파서는 원본 옆 **`.meta.json` 에 이미 박혀 있는 `source_id`+`domain`** 으로:

```
data/raw/law/law-drf-api-...xml + .meta.json{"source_id":"law-drf-api","domain":"law"}
   → rag/parsers/law/law_drf_api.py        (`-` → `_`)
```

새 소스를 붙이는 절차가 크롤러와 같은 모양이라 배울 것이 없다 — 새 소스 = 파일 1개,
같은 사이트 두 번째면 `_사이트.py` 로 승격, 사이트가 달라도 반복되면 `extract/` 로 올린다.

### 5. 공통 IR 6종 — 폭발을 실제로 막는 장치

파서 개수는 늘어도 된다. 위험한 것은 **파서마다 산출물 모양이 달라지는 것**이다. 그러면 청커도
소스마다 생기고, 골든셋 정답 ID 형식이 갈라지고, 결국 손을 못 댄다.
**모든 파서는 아래 6종만 뱉는다.**

| type | 뜻 | 현재 실측 | 앞으로 | D-004 청킹 규칙 |
|---|---|---:|---|---|
| `article` | 번호 붙은 조항 | **629** | 보험 약관 제○조 | <2,000자 = 1청크 / 이상 = 항 단위 |
| `para` | 문단 | **196** | 대부분의 안내문 | heading 밑에 모임 |
| `table` | 표 (header + rows) | **69** | 공고문 금액표, 약관 보장표 | 논리 행 + 헤더 3종 복제 |
| `heading` | 제목 (level) | **61** | 공고문 `□ 지원대상` | 경계로만 사용 |
| `aside` | 강조 박스·참고 | **22** | — | 독립 청크 후보 |
| `qa` | 질문/답 쌍 | **10** | 기관 FAQ | 통짜 1청크 |
| ~~`form`~~ | 서식 | ~~126~~ | — | **인덱싱 제외**(D-004) |
| ~~`division`~~ | 장·절 제목 | ~~36~~ | — | 경계 표시용 |

**이 6종이 맞는 근거는 D-004 판정표 자체다.** 판정 기준이 *"어느 사이트냐"가 아니라 "어떤 요소냐"* 로
적혀 있다 — 조문 / 별표 / 서식 / easylaw 본문 / Q/A. `ir.py` 는 그것을 코드로 옮기는 것뿐이다.

**계약을 기계가 지키게 한다** — IR 을 pydantic 모델로 두고 jsonl 쓰기 직전에 검증한다. 새 파서가
규격을 어기면 그 자리에서 실패한다. 조용히 이상한 청크가 생겨 6단계 점수만 떨어지는 것이 최악이다.

**얻는 것** — 새 소스를 붙여도 건드리는 파일이 한정된다.

| 무엇을 추가·변경하면 | 건드리는 곳 |
|---|---|
| 새 소스 (지자체 공고 PDF) | `parsers/subsidy/xxx.py` 1개 + (첫 PDF 면) `extract/pdf.py` |
| 청킹 전략 변경 | `chunkers/` 만 — 파서 N개 무관 |
| 임베딩 모델 교체 | `embed.py` 만 |
| DB 스키마 변경 | `load.py` 만 |

**7번째 타입을 만드는 기준** — **청킹 규칙이 기존 6종 중 어느 것과도 다를 때만** 새 타입을 만든다.
그 외에는 기존 타입 + 속성으로 표현한다. (예: 약관의 "특약"은 조문과 청킹 규칙이 같으므로
`article` + `kind:"특약"`. 텍스트가 없는 도표 페이지는 청킹 자체가 불가하므로 새 타입 후보.)

### 6. 코퍼스는 Q/A 가 아니다 — 어휘 불일치를 어디서 다루나

위 실측대로 **`qa` 는 983개 중 10개(1%)** 다. 코퍼스의 정체는 **조문 + 해설 + 표**이고, 앞으로 붙일
소스(약관·공고·교통 안내)에는 Q/A 가 거의 없어 비중은 더 떨어진다. `qa` 를 6종에 넣은 이유는 두 가지뿐이다
— 질문과 답을 쪼개면 둘 다 쓸모없어지는 **유일한 타입**이고, D-007 골든셋 14건 중 7건의 재료다.

그래서 진짜 문제는 "Q/A 가 아닌 문서를 어떻게 담나"가 아니라 **어휘 불일치**다. 사용자는
"강아지 등록 안 하면 어떻게 되나요"라고 묻는데 문서에는 "등록대상동물의 소유자는 … 등록하여야 한다"와
`20 │ 40 │ 60` 만 있다. 대응 수단을 단계에 배치해 둔다 — **한꺼번에 넣지 않는다.**
전부 넣으면 무엇이 효과였는지 알 수 없다.

| 언제 | 수단 | 상태 |
|---|---|---|
| 3단계 청킹 | **문맥 복제** — 조각만 봐도 뜻이 서게 상위 문맥을 같이 싣는다 | ✅ D-004 확정(별표 헤더 3종 복제) |
| 3단계 청킹 | **접두 문맥** — 조문 청크 앞에 `동물보호법 제15조(등록대상동물의 등록 등)`. 법령명·조문제목이 사용자 어휘에 가장 가깝다 | 파서가 `article.title` 을 살리면 무료 |
| 자연 발생 | **해설이 다리** — easylaw 문단 196개는 설명체라 질문 어휘에 가깝고 `cites` 로 조문과 연결돼 있다 | 크롤러가 meta 에 수집 완료 |
| 8단계 이후 | **하이브리드 검색** — "입마개", "제15조" 같은 정확 용어는 dense 가 약하다 | 🔶 D-003 |
| D-003 | **리랭커** | 🔶 설계만 |
| 나중 | **doc2query** — 조문마다 LLM 이 "이 조문으로 답할 수 있는 질문" 을 생성해 청크에 붙인다. 골든셋 확장에도 재사용 | 미논의 |

**판단 시점은 8단계 검문소③이다.** "질문 1을 넣었더니 제15조가 top-5 에 없다"가 눈에 보이면
그때 위에서 하나를 고른다.

### 7. 미결 — ①포맷 층에만 영향을 준다

- **PDF 파서** (`pdfplumber` / `pypdf` / `PyMuPDF`) — 비교표는 `data/README.md` 에 있다.
  **지자체 공고를 실제로 수집할 때** 정한다. 표본 없이 정하면 D-004 가 피했던 실수를 반복한다

- **Docling** — D-004 에서 ⏸보류, 재개 조건은 "약관 PDF·공고 HWP 수집 시"

셋 다 ②사이트 층·IR·청커를 건드리지 않는다. **층을 나눈 값어치가 여기서 회수된다.**

## D-019. `parsed/` 산출물 규약 — 파일 단위·ID 층·출처 링크 — ✅ 확정 (2026-08-21)

**배경** — D-018 이 "파서를 어디에 두고 무엇을 뱉을지"(IR 6종)를 정했다. 남은 것은 **그것을 파일에
어떻게 떨구고, 각 조각을 무엇으로 부를 것인가**다. 이 규약이 3단계 청커의 입력 계약이자
5단계 골든셋이 정답을 가리키는 주소 체계가 된다.

### 1. 파일 단위 — 원본 1건 = jsonl 1개

`data/processed/parsed/{raw_stem}.jsonl` (예: `law-drf-api-animal-protection-act__20260820.jsonl`).
현재 원본 28건 중 인덱싱 대상 22건 → 파일 22개.

**근거 셋이 모두 같은 방향을 가리킨다.**

1. **재생성 범위** — 파서 하나를 고쳤을 때 그 문서 파일만 다시 쓴다. 소스 단위(`law-drf-api.jsonl`
   하나에 법령 8개)로 묶으면 시행규칙 파서만 고쳐도 전체를 다시 쓴다.
   `data/README.md` 의 "뭘 바꾸면 어디부터 다시 돌리나" 표를 한 칸 더 잘게 나눈 것이다
2. **크롤러의 변경 감지와 같은 축** — `.meta.json` 의 `sha256` 은 **원본 1건 단위**다. parsed 헤더에
   `raw_sha256` 을 적어 두면 다음 실행에서 meta 와 비교해 **안 바뀐 문서는 재파싱을 건너뛴다.**
   별도 상태 파일이 필요 없다 (D-001 원칙 2 를 파싱 단계까지 연장)
3. **규약** — `data/README.md` 가 `parsed/` 를 jsonl 로 이미 정했다(디버깅·diff). 통짜 json 트리는
   그 규약을 어기면서 얻는 게 없다 — jsonl 도 한 줄이 곧 한 요소다

### 2. 파일 구조 — 1행 문서 헤더 + 2행부터 IR 요소 (문서 순서 보존)

```json
{"type":"document","doc_id":"law-drf-api-animal-protection-act__20260820",
 "source_id":"law-drf-api","domain":"law","category":"policy","subcategory":"animal-protection-act",
 "trust_level":"law","source_type":"api","format":"xml","license":"공공누리 제1유형",
 "document_title":"동물보호법","published_at":"2026-07-07",
 "source_url":"http://www.law.go.kr/DRF/lawService.do?OC=***&target=law&ID=000412",
 "citation_url":"https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=287795",
 "raw_file":"law/law-drf-api-animal-protection-act__20260820.xml",
 "raw_sha256":"a1b2…","indexable":true,
 "parser":"law_xml","parser_version":1,"counts":{"article":103,"table":0}}
```
```json
{"type":"article","id":"law-drf-api-animal-protection-act__20260820#제15조",
 "section":"제15조","title":"등록대상동물의 등록 등","head":"제15조(등록대상동물의 등록 등)",
 "paragraphs":[{"sym":"②","no":2,"text":"② … 신고하여야 한다.",
                "items":[{"no":2,"text":"2. 등록동물에 대하여 … 30일 이내"}]}],
 "chars":812}
```

`indexable:false` 인 문서(법령 웹 원문 6건, D-004)는 **파싱하지 않는다.** 출처 링크 제공자 역할만 한다.

### 3. ID 는 두 층이다 — 요소 id(파서) / 청크 id(청커)

| 원본 위치 | 요소 id (파서) | D-004 청킹 규칙 | 청크 id (청커) |
|---|---|---|---|
| 제15조 (812자, 항 7개) | `…#제15조` | <2,000자 → 1청크 | `…#제15조` **(동일)** |
| 제101조 (**3,301자**, 항 5개) | `…#제101조` | ≥2,000자 → 항 단위 | `…#제101조제3항`, `…#제101조제4항` … |
| 시행령 별표4 | `…#별표4` | 논리 행 + 헤더 복제 | `…#별표4-라`, `…#별표4-아` … |
| easylaw 소제목 | `…#h2-3` | 소제목 단위 | `…#h2-3` **(동일)** |
| easylaw Q/A | `…#qa-1` | 통짜 1청크 | `…#qa-1` **(동일)** |

**실측하면 대부분 같은 값이다** — 동물보호법 조문 103개 중 2,000자를 넘는 것은 **2건**(제101조 과태료
3,301자, 제97조 벌칙 2,757자)뿐이다. 그래도 층을 나누는 이유는 셋이다.

1. **파서는 자를 기준을 몰라야 한다.** "2,000자"는 D-004 소관이고 재개 조건이 명시된 만큼 바뀐다.
   임계값이 파서에 박히면 청킹을 바꿀 때마다 파서를 다시 돌려야 한다 — 단계를 파일로 끊은 이유가 무너진다
2. **골든셋 재작성 범위가 드러난다.** 청킹 전략을 바꾸면 청크 id 는 바뀌지만 요소 id 는 안 바뀐다
3. **청크 id 는 사람이 읽는다.** D-004 의 "청크 ID 가 곧 인용 문자열"이 이 뜻이다.
   `조문가지번호` 가 179건 있으므로 `제12조의3` 형태를 정확히 만들어야 한다

**DB 적재 시 대응** (`db/init/01_schema.sql`)

| 우리 값 | `documents` |
|---|---|
| 청크 텍스트 | `content` |
| `sha256(content)` | `content_hash` (중복 적재 방지 자연키) |
| `제15조제2항` | **`section`** (D-008 이 조항 인용용으로 만든 컬럼) |
| `동물보호법` | `document_title` |
| **청크 id 전체** | **`metadata.chunk_id`** |

`documents.id` 는 `gen_random_uuid()` 라 재적재마다 바뀌므로 골든셋 주소로 쓸 수 없다.
**6단계 베이크오프는 7단계 적재보다 먼저**라 골든셋은 파일 단계의 chunk_id 로 정답을 적을 수밖에 없고,
그 값이 DB 까지 살아남아야 적재 후에도 같은 평가셋을 쓴다. 그래서 `metadata.chunk_id` 가 필수다.

### 4. 출처 링크는 `citation_url` 로 분리한다 — 파서가 유일하게 풀 수 있는 매핑

법령 API 원본의 `source_url` 은 `lawService.do?OC=***&…` 다. **마스킹돼서 열리지 않고**(D-012·D-016
이 의도적으로 지웠다) 열려도 XML 이라 사람에게 보여줄 수 없다. 그대로 `documents.source_url` 에
적재하면 **9단계 답변의 출처 링크가 죽는다 — KPI 두 축 중 하나가 통째로 실패한다.**

바꿔치기할 수 있는 자리는 셋뿐이고, **필요한 사실(`law_serial` ↔ `lsiSeq`, 웹 원문 6건의 URL)을 쥔
층은 파서뿐**이다.

| 어디서 | 그 층이 보는 것 | 가능? |
|---|---|---|
| **파서** | 원본 + 자기 meta + 웹 원문 meta | ✅ |
| 적재기 | `parsed/`·`chunks/` 만 → `raw/` meta 를 다시 뒤져야 함 | △ 중복 |
| 앱(9단계) | DB 만 | ❌ |

**헤더에 두는 진짜 이득은 분기가 파서 안에서 끝난다는 것이다.**

| 소스 | `source_url` (받은 곳) | `citation_url` (보여줄 곳) |
|---|---|---|
| `law-drf-api` | API 호출 주소(마스킹) | 웹 원문 `lsInfoP.do?lsiSeq=…` |
| `easylaw-pet` | 웹페이지 | 같은 값 |
| (예정) 공고 PDF | PDF 파일 주소 | 게시글 페이지 |

값이 갈리는 규칙은 소스마다 다르지만 **청커·적재기·앱은 `citation_url` 한 필드만 본다.**
헤더에 두지 않으면 그 `if` 가 세 층에 복제된다.

> **정정 (2026-08-21, 구현 중 확인)** — 계획은 웹 원문(D-011)의 `lsiSeq` 와 짝짓는 것이었으나 둘 다
> 어긋났다. ① `law_serial` 은 `Extracted.extra` 에만 있고 `store.py` 가 meta 에 쓰지 않아 **`.meta.json`
> 에 없다.** ② 수의사법·자연공원법은 **웹 원문을 수집하지 않아** 짝지을 대상 자체가 없다.
> 대신 `https://www.law.go.kr/법령/{법령명}` 형식이 8종 전부 200 을 주는 것을 확인해(동물보호법 /
> 자연공원법 / 동물보호법 시행규칙) 그것을 쓴다. **한 규칙으로 8종을 덮고 항상 현행을 가리킨다.**
> 웹 원문 6건은 그대로 `indexable:false` 로 두되, 이제 링크 제공자 역할도 하지 않는다 —
> D-011 의 수집 자체는 조문 집합 대조(D-016)에 이미 값을 했으므로 되돌리지 않는다.

**요소 단위 오버라이드는 열어 둔다** — 법제처가 조문 딥링크를 쓴다(easylaw 의 관련법령 표에서 확인:
`LSW/LsiJoLinkP.do?docType=JO&lsNm=동물보호법&joNo=001500000` = 제15조). 이 형식을 우리가 만들 수
있으면 **"제15조" 인용 옆에 그 조문으로 바로 가는 링크**를 붙일 수 있어 KPI 가 한 단계 올라간다.
지금 확정하지 않고, **요소가 `citation_url` 을 가지면 그것이 문서 헤더보다 우선**한다는 규칙만 둔다.

### 재개 조건

- 청킹 전략이 바뀌어 요소 id 까지 흔들리면 → 골든셋 재작성 범위를 산출하고 이 절을 갱신
- `joNo` 형식을 실측으로 확인해 조문 딥링크가 만들어지면 → 요소 단위 `citation_url` 을 정식 채택
- 파싱 산출물이 커져 파일당 수십 MB 가 되면 → 압축(jsonl.gz) 재논의. 지금은 근거 없음

## D-020. 별표 괘선표는 셀 격자까지 파싱한다 — ✅ 확정 (2026-08-21, 별표 69건 실측)

**배경** — D-004 가 별표를 "논리 행 단위 + 표제목·단위·컬럼헤더 3종 복제"로 자르라고 확정했지만,
**"논리 행을 어떻게 만들 것인가"는 파서 몫으로 남아 있었다.** 원본은 HWP 를 고정폭 텍스트로 뽑은
괘선 아트라, 한 논리 행이 물리적으로 2~11줄에 걸치고 컬럼이 줄 단위로 뒤섞인다.

### 결정 — 표시 폭 기준 컬럼 격자를 계산해 셀 단위로 분해한다

프로토타입으로 두 방식을 같은 표·같은 행에 돌려 비교했다.

**A안 (셀 격자) — 질문 1의 정답 청크, 163자**
```
동물보호법 시행령 [별표 4] 과태료의 부과기준(제35조 관련)
(단위: 만원)
위반행위: 라. 소유자가 법 제15조제1항을 위반하여 등록대상동물을 등록하지 않은 경우
근거 법조문: 법 제101조제3항제4호
과태료 금액 1차 위반: 20 / 2차 위반: 40 / 3차 이상 위반: 60
```

**B안 (논리 행만) — 질문 3, 헤더를 복제해도 이 상태**
```
아. 소유자등이 법 제16조제2항제1호에  법 제101조  20  30  50 따른 안전조치를 하지 않은 경우  제4항제4호
```

**B안을 기각한 결정적 이유** — 위반행위 문장이 `법 제101조` 와 `20 30 50` 을 사이에 끼고 두 동강 나고,
근거 법조문이 `법 제101조` / `제4항제4호` 로 갈라져 **`제101조제4항제4호` 라는 인용 문자열을 복원할 수
없다.** D-004 가 구조 기반 청킹을 고른 이유("청크 ID 가 곧 인용 문자열")가 이 지점에서 무너진다.
금액이 몇 차 위반인지도 청크 안에서 확정되지 않는다.

### 알고리즘 (약 80줄)

1. `별표내용` 에서 빈 줄을 걷어내고 **괘선 구간 / 텍스트 구간**으로 나눈다 (별표 4 는 999줄 → 텍스트 23 + 표 304)
2. `│` 의 위치를 **동아시아 문자폭(한글 2칸) 기준**으로 계산한다. 문자 인덱스로는 정렬되지 않는다 — 원본이 표시 폭으로 패딩돼 있기 때문
3. 데이터 행에서 **최빈 `│` 배치 = 컬럼 경계**. 헤더는 병합 셀이라 배치가 다르다
4. `├──┼──┤` 이전 = 헤더, 이후 = 본문. 헤더 셀이 여러 컬럼에 걸치면 **걸친 컬럼 전부에 그 텍스트를 배분**한다
   (`과태료 금액` + `1차` + `위반` → `과태료 금액 1차 위반`)
5. 논리 행 경계는 **빈 셀 행**(`│  │  │  │`) 또는 `├` 구분선. `가./나./다.` 마커보다 확실하다 —
   원본 표의 행 경계가 그대로 남은 신호다
6. `├` 가 하나도 없으면 헤더/본문 구분이 없는 표다 (도식·수식 박스). 전부 본문으로 본다

### 실측 — 별표 69건 전체 분포

| 분류 | 건수 | 처리 |
|---|---:|---|
| **데이터 표** | **25** | `table` 요소. 헤더 2~7칸. 과태료 2종(66행·99행), 보험금액, 행정처분, 자격시험, 수수료 … |
| 단일 칸 도식·수식 박스 | 7 | **`aside`** 로 분류. 과징금 산식(`부과금액 = 1일 평균매출 × 정지일수 × 0.1`) 등 내용이 있어 버리면 안 된다 |

| 표 없는 순수 텍스트 | 33 | `para` |

반려견 도메인에서 실제로 필요한 표는 전부 25건 쪽에 있다. 나머지 11건은 축산·검역용이고 애초에 표가 아니다.

### 수용하는 아티팩트 2개

- **`제16조제2항제1호에따른`** — 원본이 셀 폭에 맞춰 임의 위치에서 줄바꿈하므로 이어붙일 때 띄어쓰기가
  하나 사라질 수 있다. **공백을 넣으면 `위반하 여` 가 되므로 넣지 않는다.** 검색·인용에 영향이 없어 수용한다

### 재사용

이 코드는 `rag/extract/` 의 **포맷 층**에 둔다. 앞으로 올 **지자체 공고문 금액표·펫보험 약관 보장표**가

## D-021. 3단계 청커 — 입력 범위·길이 기준·조립 규칙 — ✅ 확정 (2026-08-24, ①~⑤ 전부)

**배경** — D-004(청킹 전략)와 D-019(parsed 규약)가 확정된 뒤 3단계 청커에 들어갔다. 그런데 둘 다
**"어디를 자르나"**만 정했고 **"무엇을 넣고, 무엇으로 재고, 어떤 모양으로 떨구나"**는 정한 적이 없다.
청커를 짜려면 다섯 개를 더 정해야 하고, 이 ADR 하나에 모은다 — 다섯이 한 단계의 규칙이라
쪼개면 서로를 참조하는 ADR 이 다섯 개 생긴다.

### 논의 순서와 그 이유

뒤 결정이 앞 결정을 되돌리게 만들지 않는 순서다.

| 순 | 결정 | 상태 | 이 자리인 이유 |
|---|---|---|---|
| ① | **입력 범위** — 부칙 224건 · 별표 aside | ✅ 확정 | "무엇을 자를 것인가"가 먼저. 대상 집합이 정해져야 규칙을 짤 대상이 확정 |
| ② | **길이 기준** — 문자 vs 토큰 | ✅ 확정 | ③에서 숫자를 말하려면 *자*가 먼저 |
| ③ | **`content` 조립 규칙** | ✅ 확정 (2026-08-24) | 본체. ①②가 입력과 자를 고정한 뒤라야 논의가 닫힘 |
| ④ | **길이 초과 시 폴백** | ✅ 확정 — **규칙 없음** | ③ 결과물 길이를 봐야 필요 여부가 판명 |

### 재논의 비용은 결정마다 10배씩 다르다

"새 소스를 수집하면 전략을 다시 세울 수 있나"에 대한 답이다. **청킹 규칙은 *소스*가 아니라
*IR 타입*에 걸린다**(D-018). 펫보험 약관 `제12조`는 파서가 `article` 로 뱉으므로 조문 규칙을
코드 수정 없이 그대로 탄다. 규칙이 정말 안 맞으면 `article` + 속성으로 분기하거나 7번째 타입을
만드는 것이 D-018 이 이미 정해 둔 정상 경로다.

| 결정 | 성격 | 나중에 바꾸면 | 비용 |
|---|---|---|---|
| ① 입력 범위 | 소스별·타입별 | 그 소스만 재청킹 | 🟢 |
| ③ content 조립 | 타입별 | 재청킹 + 재임베딩. 경계가 그대로면 `chunk_id` 가 안 바뀌어 **골든셋은 생존** | 🟡 |
| ⑤ 산출물 규약 | 전역 (필드 추가는 언제나 가능) | 필드 추가=무료 / 의미 변경=재청킹 | 🟢~🟡 |
| ② 길이 기준 | 전역 | 전면 재청킹 | 🔴 |
| 경계·ID 체계 | 전역 | **골든셋 재작성** (D-019) | 🔴🔴 |

비싼 것은 ②와 경계/ID 둘뿐이라 그 둘을 앞에 놓았다.

### ① 입력 범위 — ✅ 확정 (2026-08-22)

**실측 (파싱 22건 기준)**

| 관측 | 수치 |
|---|---:|
| 부칙 총 건수 | 224 |
| 서로 다른 본문 | 191종 → **33건이 완전 중복** |
| 최다 중복 | `이 규칙은 공포한 날부터 시행한다.` **x12** |
| 타법개정 부칙(제목에 괄호) | **96건 (43%)** |
| `생략` 포함 | 86건 |
| 조 구조 있음 / 단문 | 118 / 106 |
| 질문 1~7 키워드가 걸린 것 | 3건 |

**중복 33건은 노이즈가 아니라 조용한 소실이다.** D-008 이 `content_hash` 를 중복 방지 자연키로
잡았기 때문에 8개 법령에 똑같이 든 `이 법은 공포한 날부터 시행한다.` 는 **적재 시 1건으로 합쳐진다.**
어느 법령의 부칙이었는지가 사라지는데 에러는 나지 않는다.

**반대로 버리면 아까운 것도 실재한다** — 동물보호법 부칙 제11조(맹견사육허가에 관한 경과조치)
*"이 법 시행 당시 맹견을 사육하고 있는 자는 … 시행일 이후 6개월 이내에 맹견사육허가를 받아야 한다"*.
질문 5 의 실질 답변 절반이 여기 있다. 본문 제18조① 은 "허가를 받아야 한다"까지만 말한다.

**결정 — 구조 기반 선별 (전부 인덱싱 ✗ / 전부 제외 ✗)**

1. **타법개정 부칙 제외** — 제목이 `부칙(다른 법령명)` 형태. 이 법에 대한 규범이 아니라 남의 법 개정 부산물
2. **남은 부칙은 부칙 조 단위로 청크** — `#부칙-2022042618853제11조`. 지금은 부칙 하나가 통짜 `para`
   (최대 5,779자)라 그대로 두면 ②의 한계에도 걸린다. **자르는 것은 청커 소관이라 파서는 건드리지 않는다**(D-019 두 층)
3. **조가 없는 단문 시행일 부칙은 청크를 만들지 않는다** — 시행일은 이미 문서 헤더 `published_at` 과
   `article.effective_date` 에 있다. 정보가 중복일 뿐 아니라 **이것이 중복 33건의 정체**다

**별표에서 나온 `aside` 5건 제외** (easylaw ※박스 22건은 질문 7 의 유일한 정답이므로 당연히 유지).

> **보강 (2026-08-24, ④ 에서 발견)** — 제목만으로는 못 거르는 것이 둘 더 있었다.
> ① 부칙 **안의** `제N조(다른 법률의 개정)`, ② **헤더가 전무한 표 9개**(전부 서식).
> 상세와 근거는 **④ 의 「① 보강」** 절에 있다. 제외 결과 1,424 → **1,403 청크**.

> **D-020 경고 문구 정정** — "별표 12: 격자를 못 세운 괘선 구간"은 **데이터 소실이 아니었다.**
> 별표 12 본문은 `para` 3,843자 + `table` 5개로 전부 정상 파싱돼 있고, aside 로 떨어진 2건은
> 별표 안에 박힌 **계약서 서식 조각**(`매매금액 / 금 원 정 / 서명 (인)`, `현재 상태 [ ]양호`)이었다.
> 격자 계산 실패가 아니라 **애초에 표가 아닌 것(서식)을 표로 읽으려 한 것**이고, 서식은 D-004 가
> 이미 "빈 양식 필드 텍스트라 검색 노이즈"로 제외 판정한 종류다. 경고 문구를 "서식 혼입"으로 고친다.

   bge-m3 파생이라 vocab 을 그대로 물려받았다. **토크나이저는 3종이 아니라 실질 2종**이다
2. **Qwen3 별표행 최악 비율 0.95** — 1자당 토큰이 1개를 넘는다. 숫자·괘선 기호가 많은 표 행에서
   문자보다 토큰이 더 나온다. "문자가 토큰보다 많다"는 직관은 우리 코퍼스에서 안전하지 않다

**잠정 결론 (B안)**

- **자르는 자는 문자.** 토큰으로 자르려면 *어느 토크나이저로* 자를지를 정해야 하고, bge-m3 토크나이저로
  자른 청크는 bge-m3 에 맞춰진 청크라 **6단계 3파전이 오염된다.** 토크나이저가 2종뿐이라 "평균"이라는
  절충도 성립하지 않는다. 문자 기준만이 **청크 1벌을 3모델이 공유**한다는 4단계 전제와 양립한다
- **토큰은 4단계 임베딩 직전의 가드**로 쓴다 — 각 모델 토크나이저로 재서 한계 초과 청크가 하나라도
  있으면 실패시킨다. D-004 기준④(임베딩 입력 한계)가 실제로 집행되는 자리는 여기다. 지금은 초과하면
  조용히 잘린다
- **하드 상한 7,500자** — 실측 최악 0.95자/토큰이므로 어떤 내용이 와도 7,900토큰을 넘지 못한다.
  구속하는 것은 bge-m3/KURE 의 8,192 이고 Qwen3 는 사실상 무제한이다
- **D-004 의 "2,000자"는 그대로** — 2,000자 조문은 약 1,120토큰이라 한계와 무관하다. 그것은 한계 규칙이
  아니라 기준③(검색 단위 = 답변 단위) 규칙이었다

> **D-004 정정** — 근거로 쓴 `8,000자 ≈ bge-m3 한계 근사`는 최악 케이스에서 8,421토큰이 되어 한계를
> **넘는다.** 판정표에 남은 규칙이 아니라 별표 분할의 필요성을 보인 근거일 뿐이라 결론은 바뀌지 않는다.

**유통기한 — 명시한다 (2026-08-24 확정)**

> **문자 기준은 6단계 베이크오프까지다.** 유일한 근거가 "토크나이저로 자르면 3파전이 오염된다"인데,
> 7단계에서 승자 1종만 남으면 그 근거가 소멸한다. 이후 토큰 기준 전환은 **승자 확정 후 별도 판단**으로 넘긴다.

적지 않으면 근거가 사라진 뒤에도 규칙만 관성으로 남는다. ADR 을 쓰는 이유가 그것이다.

### ③ `content` 조립 규칙 — ✅ 확정 (2026-08-24)

#### 논의 전에 못 박아 둔 관점

지금 다섯 결정은 **법령 코퍼스 하나만 보고** 정하는 것이다. ③(`content` 조립)에서 법령만 보고
최적화하면 다음 소스에서 깨진다.

- **지자체 공고 HWP** — `heading + para` 라 구조는 쉬운데 문서 제목(`2026년 반려동물 등록 지원사업 공고`)이
  **그 자체로 검색 키**다. "문서 제목을 청크 앞에 붙이나"를 법령만 보면 `동물보호법 시행규칙` 이 별 도움
  안 돼 보이지만 공고문에서는 결정적이다. **③은 "공고문이 왔을 때도 말이 되나"를 같이 보고 정한다**
- **펫보험 약관 PDF** — 조문 구조는 비슷하나 표가 셀 병합투성이라 D-020 의 고정폭 격자가 안 먹는다
  (D-020 이 이미 "PDF 표는 라이브러리가 셀을 주므로 (2)(3)은 건너뛴다"고 적어 둔 그대로)

#### 판단 기준 — "본문에서 복원 가능한가"

붙일지 말지를 타입마다 감으로 정하면 소스가 늘 때마다 다시 감으로 정하게 된다. 기준을 하나 잡았다.

**청크를 떼어놓고 봤을 때, 사용자 질의에 들어갈 말이 텍스트 안에 있는가.** 없으면 넣고, 본문이 이미
말하고 있으면 넣지 않는다. 단서가 하나 붙는다 — **질의어가 될 수 있는 것에 한해서**다.
`동물보호법` 은 사용자가 실제로 치는 말이고 `반려동물과 생활하기`(사이트 분류)는 아니다.

#### (가) 문서 제목 — 전 타입에 붙인다

**법령 조문은 자기 이름을 절대 말하지 않는다.** 이것이 이 절의 핵심 실측이다.

| 조문 종류 | n | 자기 법령명이 본문에 등장 | "이 법/영/규칙" | "법 제○조" 참조 |
|---|---:|---:|---:|---:|
| 법률 | 375 | **0%** | 13% | 1% |
| 시행령 | 78 | 0% (모법명 6%) | 8% | 85% |
| 시행규칙 | 176 | 0% (모법명 4%) | 10% | 86% |
| easylaw para | 196 | 「법령명」 47% | — | — |

시행령·시행규칙의 85%가 `법 제101조제3항제4호` 라고 쓰는데 **그 "법" 이 어느 법인지 청크 안에 없다.**
코퍼스에 법률이 넷(동물보호법·가축전염병예방법·수의사법·자연공원법) 있어 실제로 모호하고,
답변에 "법 제101조" 라고 실으면 **출처가 되지 않는다 — 인용 KPI 가 직접 깨진다.**

`제101조(과태료)` 가 본문에 있는 것은 **조 번호이지 법령명이 아니다.** 이 둘을 혼동하면
"법령명은 이미 있으니 안 붙여도 된다" 는 잘못된 결론에 이른다.

**easylaw 는 문서 제목이 사이트 경로 전체**(`반려동물과 생활하기 > … > 반려견과 외출 시 이것만은
챙기세요. (본문)`, 70자)라 그대로 붙이면 중앙 청크의 20%, 최소 청크(75자)의 93%가 캡션이 된다.
앞 3단은 복원 불가지만 질의어도 아니다 → **마지막 마디만** 쓰고 `(본문)`·`(100문 100답)` 접미사는
수집 아티팩트라 제거한다.

> **정정 (2026-08-24) — qa 는 예외다.** "전 타입" 에서 `qa` 를 뺀다. 문서 제목 마지막 마디가
> `반려동물을 지켜주세요.` 처럼 **사이트 문구**이고, (가)의 단서("질의어가 될 수 있는 것에 한해서")를
> 문자 그대로 적용하면 붙일 대상이 아니다. 게다가 qa 10건이 캡션 5종을 나눠 써(3·2·2·2·1)
> 붙이면 서로 비슷해지는 손해만 남는다. **대신 붙일 것이 따로 있다 — (마) 정정 참조.**

#### (나) `table` — 분할 행은 `헤더: 값`, 통짜 표는 헤더줄+값줄

D-020 격자 파서 덕에 **한 규칙으로 89표를 덮을 수 있다**: 헤더 없는 표 0개, 헤더 칸수 ≠ 행 셀수인 행
**0행**(3,165셀 전부 정합). 칸수는 2~7로 흩어져 있어 규칙이 칸수에 의존하면 안 된다.

분할 대상 372행을 실제로 조립해 봤다.

| 방식 | 중앙 | p90 | 최대 |
|---|---:|---:|---:|
| 셀만 이어붙임 | 68자 | 229자 | 2,662자 |
| **A** 캡션 + `헤더: 값` 줄 | 159자 | 270자 | 3,559자 |
| B 캡션 + 헤더줄 + 값줄 | 170자 | 295자 | 3,561자 |

**A 를 고르는 이유는 길이가 아니라 거리다.** 질문 1("등록 안 하면 어떻게 되나요")이 이 행과 만나려면
`과태료` 라는 단어가 `20` 옆에 있어야 한다. B 는 헤더가 한 줄에 몰려 값과 떨어진다. 차이는 11자뿐이라
길이로는 고를 수 없다.

**통짜 72표는 B 다.** 표 전체를 한 청크에 넣는데 행마다 헤더를 반복하면 같은 문자열이 수십 번 들어간다.
A 는 "행이 혼자 서야 할 때" 의 규칙이고 통짜 표의 행은 혼자 서지 않는다.

**빈 헤더 칸(14표)은 페어링에서 생략한다** — 붙일 이름이 없는데 `: 20` 을 만들면 노이즈만 는다.

이 조립이 (가)의 희석 우려도 해소한다. 행이 68 → 159자가 되면서 법령명 비중이 13% → **6%** 가 되고,
성격이 바뀐다 — 캡션은 덧붙인 접두어가 아니라 **`20` 을 의미 있게 만드는 본문 자체**다.

```
동물보호법 시행령 별표 4 과태료의 부과기준 (단위: 만원)
위반행위: 라. 소유자가 법 제15조제1항을 위반하여 등록대상동물을 등록하지 않은 경우
근거 법조문: 법 제101조제3항제4호
과태료 금액 1차 위반: 20
과태료 금액 2차 위반: 40
과태료 금액 3차 이상 위반: 60
```

#### (다) `article` — 재번호 없이 개행으로 잇는다

파서가 `text` 에 `①` 과 `1.` 을 이미 넣어 두었으므로 조립은 이어붙이기다.

```
동물보호법 제15조(등록대상동물의 등록 등)
① 등록대상동물의 소유자는 …
② 제1항에 따라 등록된 …
1. 등록동물을 잃어버린 경우: … 10일 이내
2. 등록동물에 대하여 … 30일 이내
```

2,000자 초과 12건을 항 단위로 자를 때 **각 청크가 `법령명 + head` 를 반복한다.** 반복하지 않으면
`③ …100만원 이하의 과태료` 청크가 어느 조인지 잃는다.

#### (라) easylaw 헤딩 — h1 도 넣는다

처음 제안은 "h1 제외" 였고 **틀렸다.** h1 20개를 전부 열어 보니 두 종류였다.

| 종류 | 수 | 예 |
|---|---:|---|
| 서술문 | 12 | `외출 시에는 목줄…준비해 주세요.` · `반려견이 맹견이라면 ?` |
| **명사구 라벨** | **8** | `기차` · `비행기` · `시내버스` · `그 밖의 교통수단` · `반려견·반려묘 장례 등 치르기` |

**h2 41개 중 `이동장비에 넣는 등 안전조치를 취한 후 탑승하기` 가 4번 반복된다** — 시내버스·고속버스·
전철·기차 밑에 같은 문자열로 붙어 있다. `(h1, h2)` 쌍으로는 중복이 0 이므로 **넷을 구분하는 축은 h1 뿐**
이다. 빼면 네 청크의 캡션+제목이 완전히 같아지고 "강아지 기차 탈 수 있어?" 가 무엇을 집을지 알 수 없다.

서술문 쪽에도 필요한 사례가 있다. `등록대상동물, 정보 변경이 있다면 신고해야 합니다.` 밑의 h2 가
**`잃어버린 경우`(174자)** 다 — h1 이 없으면 무엇을 잃어버린 건지 청크 안에 없다. 질문 2 바로 옆이다.

**처음 논거의 오류** — D-004 가 대단위(`인쇄체크`)를 버린 것을 근거로 들었으나 그것은 **청크 경계**
결정이었다. 경계로 쓰면 2,000자에 주제 4개가 한 청크에 들어가 기준③을 위반하지만, **캡션으로 쓰면
청크는 여전히 h2 단위이고 h1 은 21자다.** 같은 텍스트라는 이유로 두 결정을 같은 것으로 취급했다.

비대칭이 결정했다 — 넣어서 생기는 피해는 형제 주제어 혼입에 따른 **순위 흔들림**(본문이 자기 주제어를
더 많이 가져 대체로 이긴다), 빼서 생기는 피해는 **구분 불가**(벡터로 갈라낼 방법이 없다).

```
반려견과 외출 시 이것만은 챙기세요.                       ← 문서 제목 마지막 마디  18자
외출 시에는 목줄 (가슴줄)·인식표 및 배변봉투를 준비해 주세요.   ← h1                21자
반려견 인식표 부착하기                                  ← h2                15자
<본문>
```
캡션 54자 / 본문 중앙 350자 = **15%**. 최소 청크(`택시` 75자)에서 29%까지 오르지만, 그 청크야말로
캡션이 없으면 식별 자체가 안 된다.

#### (마) `aside` · `qa`

- **`aside`** — `title`(`※ 반려동물과 정부 지정 자연공원 이용하기`)을 포함하고 `lines` 를 개행으로 잇는다.
  마지막 줄 `(「자연공원법」 제29조 제1항 … 참조)` 도 **유지한다** — 질문 7 의 유일한 정답인데다
  그 줄이 출처 조항 번호 자체라 KPI 에 직접 기여한다
- **`qa`** — `question` + `answer` + **`관련 법령:` 줄**

> **정정 (2026-08-24) — `related_laws` 를 본문에 넣는다.** D-004 판정표의 "관련법령은 본문에서 빼고
> 메타로" 를 뒤집는다. D-004 는 이유를 적지 않았고, content 조립은 ③ 이 인수한 영역이다.
>
> 근거는 (가)의 핵심 실측과 **같은 병리**다 — qa 10건 중 본문(question+answer)에 법령명이 있는 것이
> **2건뿐**이다. 조문 375개의 법령명 복원율이 0% 라서 문서 제목을 붙이기로 했다면, 여기서 예외를 둘
> 근거가 없다. `related_laws` 는 9/10 이 갖고 있고 중앙 68자로 본문 639자의 11% 다.
> 9단계 답변이 인용할 조항 번호가 텍스트 안에 있게 되므로 KPI 에 직접 기여한다.
>
> **5단계로 넘기는 주의사항** — 골든셋 14건 중 7건이 easylaw Q/A 인데, qa 질문을 질의로 쓰면 그 qa
> 청크가 자기 질문을 통째로 담고 있어 무조건 top-1 을 먹는다. `related_laws` 를 넣든 안 넣든 생기는
> 문제다. 5단계에서 "정답을 qa 청크로 볼 것인가, `related_laws` 가 가리키는 조문 청크로 볼 것인가"를
> 정해야 하고, **후자여야 평가가 의미를 갖는다.**

> **정정 (2026-08-24, ④ 에서 발견)** — 위는 `aside` 의 *조립 방식*만 정하고 **소속**을 정하지 않았다.
> **`aside` 는 소제목 그룹에 흡수시키지 않고 독립 청크로 만든다.** 근거와 수치는
> **④ 의 「③(마) 정정」** 절에 있다.

### ⑤ 산출물 규약·필드 — ✅ 확정 (2026-08-24)

**판단 기준 — 누가 이 파일을 읽고, 그 층이 다른 파일을 또 열어야 하는가.**

| 읽는 층 | 쓰는 것 | 파일 경계 |
|---|---|---|
| 4단계 임베더 | `content` | 무시하고 전부 이어 붙인다 |
| 5·6단계 골든셋·평가 | `chunk_id` | 무시 |
| 7단계 적재기 | 전 필드 → `documents` 행 | 청크 행 1개 = DB 행 1개 |
| 검문소①③ | 사람이 눈으로 | 파일 단위로 연다 |

#### (A) 파일 구조 — 1행 헤더 + **자기완결 청크 행**

`data/processed/chunks/{raw_stem}.jsonl`. 원본 1건 = 파일 1개로 parsed 와 같은 축이고, 헤더에는
`parsed_sha256` 을 적어 **재청킹 스킵**을 판단한다(크롤러의 `sha256` → parsed 의 `raw_sha256` →
chunks 의 `parsed_sha256`. D-001 원칙 2 를 한 단계 더 연장).

문서 수준 값(`document_title`·`citation_url`·`category` …)은 **행마다 복제한다.**

> **D-019 와 반대 방향인 이유** — D-019 는 parsed 에서 이 값들을 헤더에 몰았고 근거는
> "`citation_url` 분기가 청커·적재기·앱 세 층에 복제된다" 였다. **청크 단계에서는 그 분기가 이미
> 파서에서 끝나 값만 물려받으므로 같은 근거가 성립하지 않는다.** 반대로 하류 세 층이 전부 파일
> 경계 없이 쓰기 때문에 헤더에 두면 그 세 층이 헤더를 들고 다녀야 한다. 1,403행 복제 비용은 200KB 다.

#### (B) `chunk_id` — 요소 id + 자른 위치, 인용 문자열은 `citation` 으로 분리

| 원본 | `chunk_id` |
|---|---|
| 제15조 (2,000자 미만) | `…#제15조` (요소 id 그대로) |
| 제101조 (2,000자 이상) | `…#제101조③`, `…#제101조④` … |
| 별표 4 행 (마커 있음·유일) | `…#별표 4-2-라` |
| 별표 4 행 (마커 없음·중복) | `…#별표 4-2-r7` |
| 부칙 조 | `…#부칙-2024010219880제2조` |
| easylaw 소제목 / `aside` / Q/A | `…#h2-3` / `…#note-1` / `…#qa-1` (요소 id 그대로) |

**실측 — 1,403 청크에서 `chunk_id` 중복 0건.** 이 체계로 유일성이 성립한다.

`citation` 을 따로 두는 이유는 D-019 §3 의 "청크 id = 인용 문자열" 이 별표에서 깨지기 때문이다 —
별표 논리 행 797개 중 마커를 가진 행이 **56%**(447), 분할 대상 372행으로 좁혀도 61%, 그 안에서
**마커 중복이 35건**이다. 마커는 유일 키가 아니다. `chunk_id` 는 주소, `citation` 은 사람이 읽는 말이다.

#### (C) 필드

| 갈 곳 | 필드 |
|---|---|
| `documents` 컬럼 직결 | `content` · `section` · `document_title` · `source_url` · `category` · `subcategory` · `source_type` |
| `documents.metadata` | `chunk_id` · `raw_file` · `format` · `trust_level` · `published_at` · `license` · `citation_url` |
| 우리만 쓰는 것 | `citation` · `doc_id` · `element_id` · `element_type` · `part` · `chars` |

`part` 는 ① 이 정한 `supplementary`(부칙) 표시다. 6단계에서 부칙이 top-5 를 오염시키면 재청킹 없이
필터로 끌 수 있는 자리이고, ① 이 "되돌리는 비용의 비대칭" 을 근거로 부칙을 넣기로 한 전제가 이 필드다.

#### (D) `content_hash` — 청커가 계산하지 않는다. 대신 중복을 **경고**한다

`content_hash` 는 DB 중복 적재 방지 자연키(D-008)이고 청크 파일은 DB 가 아니다. 계산은 7단계 적재기 몫이다.

다만 **청커가 같은 `content` 를 셋 이상 만들면 경고한다.** 서식 9표를 제외한 뒤 남는 중복은 **5건**이고,
가축전염병 시행령 별표 3(과태료 부과기준)에서 `2) 식용란의 수집판매업자 | 50 | 100 | 200` 같은 행이
상위 항목 둘 아래 실제로 두 번 나오는 경우다. 적재하면 `content_hash` 로 5행이 합쳐지는데 **에러는
나지 않는다** — ① 이 부칙 33건에서 발견한 "조용한 소실" 과 같은 병리가 청크 층에서 재발한 것이다.
합쳐지는 것 자체는 옳다(내용이 같다). **조용한 것이 문제**이므로 경고로 드러낸다.

#### ⑤ 재개 조건

- 7단계 적재에서 `content_hash` 충돌이 경고 건수(현재 5)보다 많이 나오면 → 청커 경고가 새고 있는 것
