# 작업 방식 — 우선순위·스프린트·PR

> 출처: 2026-08-22 협업 특강(이동규 멘토). 강의노트·녹취록·원문 인용은
> [choiyc05/0822_coop](https://github.com/choiyc05/0822_coop) 에 있다.
>
> 여기에는 **이 레포의 작업이 실제로 이 규칙 때문에 달라지는 것만** 옮겼다.
> 회고(열기구 패턴)·데일리 스크럼은 팀 단위 활동이라 개인 파트 레포인 여기 적으면 죽은 문서가 되고,
> 인프라(Lambda 가드레일·ArgoCD)는 배포를 아직 안 정해서 지금 결정할 것이 아니다 — 셋 다 원본에 있다.

## 1. 우선순위는 사람이 정한다

**AI 에게 위임하지 않는다.** AI 는 검증에 과몰입하고 가끔 산으로 간다.

| 등급 | 기준 | 예 |
|---|---|---|
| **P0** | 없으면 프로젝트가 **아예 동작조차 못 함** | 인프라 구성, DB·스키마, **API 키 발급** |
| **P1** | **메인 피처** — 없으면 프로젝트가 의미 없음 | 파트①의 `/ask`, 파트②의 산책 적합도 응답 |
| P2/P3 | 나머지 | 캐시 고도화, 대시보드, 프론트 |

- CI/CD 는? **없어도 동작하면 P0 이 아니다**
- **보수적으로 잡아야** 일정이 다가올수록 조급함이 줄어든다
- **배정 결과는 이 문서에 적지 않는다** → §3 의 보드가 단일 소스

## 2. 스프린트 기간 → 실제 작업량

| 스프린트 | 워킹데이 | **실제 구현 가능** |
|---|---|---|
| 2주 | 10일 | **3~4일** (맥시멈 5~6일) |
| 1주 | 5일 | **2일** |

나머지는 테스트·배포·검증에 들어간다. 이 숫자를 **그대로 AI 에게 준다**:

> 스프린트가 일주일이고 작업은 3일인데, 3일 안에 끝낼 수 있는 태스크로 쪼개서 PR 로 올려줘

한 달 프로젝트에 2주 스프린트면 **회고를 한 번밖에 못 한다.** 그럴 땐 1주로.

## 3. 태스크는 PR 에 산다 — 단일 소스

**왜 이슈가 아니라 PR인가** — 이슈는 *사람이* 관리하는 것이었는데, **AI 가 관리하려면 코드에 붙어
있어야 한다.** GitHub 에서 PR 도 엄밀히 이슈고 번호 체계가 같다 (`#13`).

**PR 을 작업 "후"가 아니라 "전"에 올린다**

| | 기존 | 이 레포 |
|---|---|---|
| 시점 | 개발이 끝난 다음 | **할 일을 정리해서 먼저** |
| 내용 | 완료된 결과물 | **앞으로 할 일의 명세** |

**이 레포의 현재 운영 (2026-08-24)** — 개인 레포이고 파트가 둘뿐이라 잘게 쪼개지 않는다.

- **브랜치 하나 = 기능 하나 = PR 하나.** `feat/realtime` 이 파트② 전체를 담는다
- **할 일 명세는 PR 본문 체크리스트**에 둔다. P0/P1 배정도 거기 있고, **md 에 또 적지 않는다** —
  두 곳에 적으면 갈라지고, 갈라진 다음엔 어느 쪽이 진짜인지 아무도 모른다
- **스프린트 박스는 지금 안 쓴다.** §2 의 산식은 태스크 크기 감각용으로만 남긴다
- **Projects 보드는 아직 안 만든다** — PR 1개짜리 보드는 빈 껍데기다.
  PR 이 여러 개로 늘어나면 그때 붙인다: `Team Planning` 템플릿 → `Open Issues` 대신
  **`Open Pull Requests`** 뷰, `Status` 에 **`Hold` 추가**(안 하게 된 이유를 필요 없어짐 / 정의가
  안 됨으로 구분해 두면 리뷰 때 백로그로 되돌릴지 결정할 수 있다), `Size` 는 나를 위한 게 아니라
  **남을 위한 것**(구현이 그려지면 XS/S, 설계도 안 떠오르면 L/XL).
  여기까지 가면 **WBS 를 따로 안 그려도** Roadmap 뷰에서 보인다

## 4. 사람과 AI 의 경계

사람은 **in the loop 가 아니라 on the loop** — 앞단(우선순위)과 뒷단(결과물 유효성)에만 있는다.

| 사람이 하는 것 | AI 에게 맡기는 것 |
|---|---|
| **우선순위 설정** (P0/P1) | 프로덕트 백로그 쌓기 |
| 스프린트 기간 결정 | 스프린트 플래닝 · 태스크 쪼개기 |
| **결과물이 유효한지 검증** | 구현 · 커밋 · PR 작성 |
| **작업이 섞이지 않았는지 확인** | PR 메시지 작성 |
| **CSP 도구 선택** (종속성 판단) | 인프라 코드 생성 |

이 레포의 `CLAUDE.md` 가 이미 같은 축을 갖고 있다 — **논의 → `docs/decisions.md` 기록 → 구현.**
설계 결정(무엇을 왜)은 사람이 닫고, 그 결정을 코드로 옮기는 것은 AI 가 한다.
